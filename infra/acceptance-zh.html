验收提交物

  • 任务级：预声明代表场景、选择理由、完整运行与失败记录、版本和哈希；不要求逐个随机实例的完整解。
  • 技能级：进入／退出与接触合同、已验证配置及适用条件、关键短片段证据；未测试范围留空。
  • 实例级：高层计划、技能选择与约束、关键状态、检查清单和四类结果；段间同时检查位置、速度、支撑、抓持、剩余预算与不确定性。
  • 预算：筛查墙钟、候选数、短仿真数量及步数事先声明；耗尽即停止并记未确定，不自动升级为完整仿真。任务执行时限另行保留。
  • 代表性全程、技能探测、静态筛查分别统计。正式准入仍需评分器正反例、物理／接口完整性、适用的人工签审及独立复现，不能用筛查结果代替。

采用实例记录模板和版本化验收政策。现有 15 项任务准入 gate 的状态枚举不变；以上四类是实例证据状态，不与 gate 的 passed／partial／pending／failed 混用。

此前发布的成功、失败、录像与签审状态原样保留；新原则不追溯补签或自动提升 admitted。已有明确约定的有限代表验收批次继续保留，变更范围需另行记录。

01 · 参考专家解

证明问题可解，并验证评分器

  • 用现有的专家解即可：读仿真真值（物体位姿、接触力），用 IK/FK 等方法规划；从生成器抽出的随机初始状态出发，只通过动作接口驱动机器人，物理设定和力矩上限与 agent 相同；不瞬移、不改物性、不把物体绑在手上。不要求它和 agent 用同一套工具。
  • 用途一：证明问题可解。所记录配置可以怎样完成，不外推整个随机实例族；顺带给出过程分的上锚点和参考完成时间。Harbor 任务里也有类似的角色：一个读真值的特权规划器，只用来标可行性和参考时间，从不发给 agent。
  • 用途二：验证评分器有效。参考专家解的运行由沙箱同样的记录器记下，交给同一个 verifier 判分：必须判为成功，各阶段的完成时刻要和人工在录像上标注的一致，监视器不能误报。再加上空操作得 0、反例和漏洞运行得 0 或判无效，评分器才算从正反两面验证过（见第 04 节）。这和 Terminal-Bench 一样：oracle 要拿到预期分数，空操作要得 0。
  • 代表性验收运行录像由人工审阅，第二个人复现选定代表方案；纯静态筛查不要求录像（见第 03 节）。

参考专家解（oracle）的条件

可以

  • 读仿真真值：物体位姿、接触、物性。
  • 用 IK/FK 暴力求出中间点（关键帧），再插值成轨迹。
  • 用力矩控制或 WBC 跟踪。
  • 手工挑选、调整关键帧。
  • 用现有的专家解即可，不要求和 agent 用同一套工具。

不可以

  • 从手工摆好的状态出发：必须从生成器抽出的初始状态（或子任务起始状态）出发。
  • 换物理设定、放宽力矩上限。
  • 瞬移、改物性、把物体绑在手上。
  • 跳过某一段，用摆位置代替。
  • 绕过动作接口，直接写关节或物体的状态。

参考解能证明什么

能证明

  • 同样的物理设定、力矩上限和动作接口下，所记录的具体初始状态可以完成；不能据此保证全部随机实例。
  • 过程分的上锚点和参考完成时间。
  • 评分器有效：参考解判成功，空操作和漏洞判 0。

不能证明

  • 只凭 agent 的传感器也做得到。
  • 所有 agent 都在某一步失败时，是这一步太难还是只靠传感器做不到。

所以参考解不是 Terminal-Bench 意义上的 oracle：那里的 oracle 走和 agent 相同的接口、只用 agent 能拿到的信息，并且要拿满分。

02 · 官方轨迹与子目标场景

保留已有代表轨迹，按需切出诊断子目标

官方轨迹

  • solution/、verified/ 里的官方脚本原样保留。它们开局用 set_pos 一类方法摆位置，以 200 Hz 子步直接调用仿真，每一步读真值，所以只作特权参考轨迹：证明单个技能做得到，并提供子目标的起点。
  • 录制时官方脚本当黑盒运行；录制器从外面挂钩，记录构造参数、脚本改过的常量、物理开关、首个物理步之后的特权写入（应为零），以及全部刚体的质量和摩擦、和沙箱同格式的特权状态日志、10 Hz 全身快照、官方脚本自己的阶段时间线。
  • verifier 用和评测 agent 同一套判据，标出官方轨迹在什么时刻达到哪一步。

切成子目标

  • 从官方轨迹的录制（以后也包括参考专家解的录制）里，恢复世界参数和某一时刻的全身快照，作为子目标场景的起点（H1 已验证：恢复结果与录制完全一致）。
  • 起点之后，agent 和完整任务一样，只有传感器和关节指令；参考解读真值、摆位置的设定，agent 一样也用不上。
  • 子目标场景只用于训练、诊断和分析，单独报告，不混进主评测；主评测始终从任务的初始状态出发（子目标的起点本身就暴露了路线）。
  • 限制：任务环境之外另加的实体（如 H1 的凳子方案）目前不能从检查点重建，暂不支持。

03 · 代表性验证与人工审阅

验证代表方案与技能边界，不逐个随机求完整解

对应 R2。正式准入按声明范围审核；没有对应完整见证时，不能仅凭静态规划或分段成功宣称完整任务可解。

  1. 冻结计划与代表样本。声明层／变体、路线、关键技能、样本选择理由、筛查预算及有限完整验证清单。覆盖边界、内部和高风险接触切换，但不要求对层×样本×子任务笛卡尔积逐项完整执行。产出：分层计划与预声明覆盖表。
  2. 执行少量完整参考。在声明配置下从原始起点、通过动作接口连续运行；物理、力矩和评分条件与任务一致。声称跨后端完成时，各后端分别留证。产出：代表性全程记录、种子、哈希、判决与验收录像。
  3. 验证技能条件。检查关键可达姿态、碰撞、载荷、支撑及进出条件；必要时仅做困难动作短仿真。独立快照起点只能支持局部结论；组合执行还需验证实际交接状态。产出：技能证据、适用条件、未确定范围。
  4. 记录随机筛查。按预声明检查和预算输出四类状态，保留全部抽样、拒绝、失败和超时，不用完整解作为每个实例的前置材料。产出：实例筛查账本。
  5. 人工核对代表证据。审阅预声明全程及关键接触／反例片段，回答第 05 节三个问题，并核对阶段时间线。无录像运行可单列物理证据，不能冒充录像签审；纯静态筛查不要求录像。产出：带签名审阅和阶段对照。
  6. 验证评分器与捷径判据。完整正例、阶段正例、空操作、反例及漏洞用同一 verifier 检查；筛查通过不作为完整正例。搜索捷径失败只证明已检查范围，不自动证明所有其他路线不可能。产出：正反例与捷径证据。
  7. 重复与独立复现。对预先选定的代表种子至少重复 3 次，报告波动；第二人复现所声明的代表方案，不要求复现每个随机筛查样本。产出：重复记录和独立复现记录。
  8. 按证据等级验收。分别统计完整运行、技能探测与实例筛查，失败原因和开销全部保留。未确定和检查不通过不能计入成功。产出：范围明确的验收报告。

代表样本数量及选择理由按风险和声明范围事先确定，不统一要求每层至少 5 个完整种子。已约定的有限验收批次不自动取消。不能根据结果换掉失败 seed；结果不足时收窄声明或补充针对性证据。

04 · 评分器有效性

正例必须判对，负例必须判 0

评分器本身要先验证，否则分数没有意义。做法和 Terminal-Bench 一样：已知能做成的运行必须拿到预期的分，什么都没做或在作弊的运行必须得 0。正例来自参考专家解：用现有的专家解即可，读真值规划；它的主要用途是证明问题可解，另一个用途就是在这里验证评分器（见第 01 节）。这些正例和负例的录像，在任务验收时还要人工检查（第 05 节）。

  • 正例：参考专家解和官方轨迹的运行必须判为成功（或达到预期的阶段），阶段时间线与人工标注一致，监视器不误报。
  • 负例：空操作得 0；每个阶段的反例不得分；逃逸探针和漏洞运行判 VOID 或 0。
  • 两组都通过，评分器才能用于评测；判据、阈值或权重改动后要重跑。

05 · 人工检查任务

任务验收和改版时，人看录像回答三个问题

任务验收及相关改版时，按预声明清单审阅代表全程、关键技能及正反例录像。静态筛查不要求录像；无录像物理记录单列，不能补记录像签审。所选录像逐段回答三个问题：

人工检查看什么对应的自动检查不通过怎么办
1 没有 reward hack参考解和试跑的分数是不是靠真实的动作拿到的；反例和漏洞测试是不是都被判 0 或无效；试跑里有没有钻空子拿到的分接口和世界完整性监视、判据异常监视、反例集、rollout 来源核对修判据、补反例、加监视器，再检查一遍；修好之前任务不能入库
2 任务确实完成了参考专家解是否真的达成目标、满足约定；verifier 给出的阶段时刻和录像对不对得上（人工标注对照）阶段判据（接触证据、物体身份、保持时长、静止条件）和成功判定改判据或阈值；参考解做不到，任务标为“未就绪”
3 没有明显违反物理规律或限制仿真里有没有穿模、弹飞、悬浮、能量来路不明；参考解有没有超出关节和力矩限制、违反公开约束物理异常监视、指令模式监视、瞬移检查、世界参数哈希修仿真设置、素材（碰撞体）或监视器阈值；违规的那段参考解不算证明了可解

流程

  1. 跑一遍。参考专家解、空操作、反例、漏洞测试和难度试跑，全部交给 verifier 自动判分。产出：verdict.json 和录像。
  2. 人看录像。对每段录像回答三个问题，写明理由，标出时间点；重点看告警的位置。产出：任务检查记录。
  3. 修 verifier。人工和自动判断不一致的地方，相应修改判据、阈值、反例集或监视器，再重跑第 04 节的有效性检查。产出：修订记录。
  4. 冻结。三个问题都通过后，冻结评分器和自动处理规则；之后评测 agent 只用自动评分。产出：冻结的评分器版本。

每个任务都要提供一份人工检查清单，供任务验收时使用：针对这三个问题，写明本任务里具体看什么（目标怎样才算达到、有哪些公开约束、哪些做法算违规），以及每个阶段在录像上怎么认（任务卡字段，见任务设计第 11 节）。

06 · 自动检查流水线

每次改动都自动检查，人只看有变化的部分

对任务的人工检查只在验收和改版时做；平时每次改动都由流水线自动检查，人只看有变化的部分。

  • 静态检查：bundle 里没有可信侧内容；机器可读的任务规格格式正确（任务设计第 11 节）。
  • 空操作得 0；受改动影响的预选代表参考达到预期结果，阶段时间线与人工标注一致；筛查通过不作为完整正例。
  • 每个阶段的反例全部不得分；漏洞测试判为无效；逃逸探针全部被拒。
  • 需要物理回归时，对预声明代表种子重跑 3 次，结果在复现容差内（评测规程第 06 节）。
  • 评分模式按原规程在 N 个密封回合执行；作者侧筛查不要求先为这些回合生成完整参考解。

本次状态落实：除 H1 外的 11 项任务

任务级保留少量完整成功见证；技能级验进入／退出条件、距离、载荷、支撑位置与姿态；实例级只做预算内的可达、碰撞、支撑和衔接检查，困难片段可短仿真；执行级按观测滚动生成局部轨迹。交付高层计划、技能选择与约束、关键状态和检查结果，完整轨迹仅为代表性验证的附加证据。

有完整成功证据／通过可行性筛查／未确定／检查不通过必须分开。检查器缺失或预算耗尽记未确定；检查不通过需必要条件反例与原因。自生成场景可按已验证技能范围采样；基准采样及所有结果完整保留。既有人工签审、第二人复现与评分器检查继续单列，不要求第二人逐个复现随机实例。
