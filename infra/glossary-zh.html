02 · 问答

常见问题

参考专家解可以读真值、暴力求解吗？

可以。它只用来证明可解和验证评分器，不给 agent 用。 详见

agent 能调用哪些工具和技能？

任务卡允许的 L1–L3、VLA、IK/FK 和指定的技能，输入只能是自己的传感器结果；也可以自己写。 详见

“4 小时以上”怎么判断？

靠难度试跑：标准 agent 配置在沙箱里不限时地解，按层记录耗时和卡住的阶段。 详见

评测 agent 时要人工看录像吗？

不用，评测全自动；人工只在任务验收时检查任务和评分器。 详见

评测为什么要重复 3 次？

agent 有随机性，GPU 上的物理也不逐位重复：每个 agent 跑 3 次评测，每个交付评分 3 次取平均。 详见

agent 用了我没想到的办法，怎么算？

按它实际达到的状态自动给分，跳过的阶段不补发；暴露出漏洞或捷径就改版、自动重评。 详见

第 2 层和第 3 层有什么区别？

第 2 层的物体换一种身体就能用，考自我建模；第 3 层是干扰项，考做实验、排除选项。 详见

子任务场景为什么不给被评测的 agent？

子任务的起始状态本身就暴露了路线。 详见

只做 Genesis 可以吗？

可以，Isaac Lab 对齐是推荐项。 详见

我要用 Go1，可沙箱还没有 Go1 的传感器？

把补上 Go1 传感器仿真作为任务的一部分。 详见

oracle 做不出全链路怎么办？

若声明范围没有代表性完整见证，不能以筛查或分段成功替代完整验收；可先提交规划和局部证据。某个随机实例在预算内没找到完整解则记未确定，不因此把整个任务或该实例判为不可解。详见

03 · 参考了什么

Terminal-Bench（Harbor）和 EmbodiedSWE

下表对比两者和我们的做法。Terminal-Bench 一栏以本地的 Harbor 格式任务（Benchmark/tasks/g1_support_augmented_retrieval）为准，EmbodiedSWE 一栏以本地仓库 EmbodiedSWE/eval 和 robobench 为准。

环节Terminal-Bench / HarborEmbodiedSWE我们
agent 在哪里任务的环境容器里；agent 阶段可以断网（network_mode = "no-network"）Docker 容器，非 root 用户 agent，只有 /workspace 可写；隔离网络时只经 squid 白名单出网Linux 容器：uid 1000、根文件系统只读、丢弃全部 capabilities、no-new-privileges、限制进程数、内存和 CPU；内部网络，唯一出口是通往环境的 RPC 端口（可选 squid 白名单通 LLM API）
agent 能看到什么指令和环境镜像；测试不在镜像里只读挂载的 /bench 和 /task；评分器“永远不在 agent 能看到的目录树里”，构建时还会扫描泄露只有机器人传感器读数、指令、机器人模型和 SDK；仿真、评分、日志都在另一边
环境怎么防改—（终端任务，不涉及物理世界）包装器让 reset、set_states 抛异常，构建时冻结控制模式；其他属性仍委托给原始环境agent 根本拿不到环境对象，只有 8 个 RPC 方法；没有任何改世界的方法
交付物指定的产物目录（如 /app/methods）提交到 /submissions 的 solve.py只调用 SDK 的控制程序（工作目录）
评分器在哪里单独的 verifier 镜像（environment_mode = "separate"），测试目录权限 700，断网事后另起一个容器，评分器只读挂载，不带凭据环境一侧：和仿真、记录器、监视器在同一个可信边界里
评分时交付程序在哪里跑在 verifier 容器的文件系统里，每个回合一个子进程（nobody 用户、rlimits、seccomp 禁网络和 ptrace）；仿真在父进程里被导入评分器的同一个 Python 进程，通过包装后的环境运行每个回合一个全新的 agent 容器和工作目录副本，只经 RPC 和环境通信；永远不进环境一侧
密封测试集密封回合文件，先核对 sha256，再在运行提交代码之前删除按 --seed 和环境数重新随机；默认种子是 0可信侧私下抽取的种子，按任务类型分层；开发和评测还没有分成不同的种子集合
分数reward.json，出错强制为 0（fail-closed），先删除旧的奖励文件rubric：阶段分 once / live / final，进度峰值为分，success 单独给；部分任务加 VLM 终判沿用 EmbodiedSWE 的 rubric 思路：阶段连续取值、进度峰值、成功单独给；全自动
评分器怎么证明有效oracle 解应拿到预期分数（本地任务为 0.6），空操作应得 0；逃逸测试（读答案、改评分、搜磁盘、联网）全部 0 分—参考专家解和官方轨迹判成功、与人工标注一致；空操作、反例、漏洞运行得 0 或无效
防作弊测试不可见、密封集、逃逸测试（读答案、改评分、搜磁盘、联网等全部 0 分）靠访问控制加规则；仓库里没有监视器或对话审计逃逸探针、违规即无效、世界参数哈希、瞬移检查；监视器和防编造见评分与验证页
锚点oracle 解应拿到预期分数（本地任务为 0.6），空操作应得 0（--agent oracle / nop），既证明可解，也证明评分有效；另有一个读真值的特权规划器，只用来标可行性和参考时间，从不发给 agent—参考专家解和官方轨迹给上锚点并验证评分器，空操作得 0

借鉴的做法

  • Terminal-Bench：评分器与 agent 分开、测试不可见、密封的留出回合、出错即判 0、用 oracle 和空操作同时证明可解和评分有效、逃逸测试。
  • EmbodiedSWE：rubric 评分器（once / live、进度峰值、成功单独给）；评分器永远不进 agent 的目录树；把交付程序放到新回合上重跑；内部网络加白名单代理；agent 不是 root。

刻意避开的问题

  • EmbodiedSWE 把交付的 solve.py 导入评分器进程，包装器只拦了 reset 和 set_states，原始环境仍可访问。本沙箱的交付程序和环境、评分器不共用进程，也不共用容器。
  • EmbodiedSWE 的对话记录写在 agent 可写的工作目录里。本沙箱由启动器在容器外记录 agent 的输出。
  • EmbodiedSWE 评分默认用种子 0，可能和开发时的初始状态相同。本沙箱的评分种子由可信侧私下抽取。
  • EmbodiedSWE 的说明里写着“不作弊靠提示词，而不是访问控制”。本沙箱全部靠访问控制。
  • Harbor 的提交代码在 verifier 的文件系统上运行，要靠删除密封文件、nobody 用户和 seccomp 防护。本沙箱的交付程序根本不进环境一侧。
随机实例必须都有完整轨迹吗？

不需要。任务级有少量代表完整见证，技能级验证适用条件，实例级在预算内筛查，执行时滚动生成局部轨迹。筛查通过、未确定、检查不通过与完整成功证据分开记录。验收标准
