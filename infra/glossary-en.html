02 · Questions

Common questions

May the reference expert read ground truth and brute-force the solution?

Yes. It only proves solvability and validates the verifier; the agent never uses it. Details

Which tools and skills may the agent call?

The L1–L3, VLA and IK/FK tools and designated skills the task card allows, fed only by its own sensor results; it may also write its own. Details

How is "more than 4 hours" judged?

With the difficulty pilot: standard agent configurations work without a time limit, and time and sticking points are logged per layer. Details

Does anyone watch videos when agents are evaluated?

No, evaluation is fully automatic; people check only the task and its verifier at acceptance. Details

Why is every evaluation repeated 3 times?

Agents are random and GPU physics is not bitwise repeatable: each agent runs 3 evaluations, and every delivery is scored 3 times and averaged. Details

The agent used a method I did not anticipate. How is it scored?

Automatically, by the states it reaches; skipped stages are never back-filled; a revealed hole or shortcut leads to a new version and automatic re-grading. Details

What is the difference between layer 2 and layer 3?

Layer-2 objects would work for another body and test self-modelling; layer-3 distractors test experimenting and ruling options out. Details

Why are subtask scenarios not given to the agent under evaluation?

A subtask's start state reveals the route. Details

Is Genesis alone enough?

Yes; Isaac Lab parity is recommended. Details

I want to use Go1, but the sandbox has no Go1 sensors yet.

Adding Go1 sensor simulation is then part of your task. Details

What if the oracle cannot do the full chain?

Without a representative complete witness for the declared scope, screening or segment successes cannot replace full acceptance; plans and local evidence may be submitted first. An unresolved random instance is unknown, not a declaration that the task or instance is impossible. Details

What we adopted

  • Terminal-Bench: a verifier separate from the agent, hidden tests, sealed held-out episodes, fail-closed rewards, using the oracle and a no-op to show both solvability and that grading works, escape tests.
  • EmbodiedSWE: rubric graders (once / live, peak progress, separate success); graders never in the agent's tree; re-running the delivered program on new episodes; an internal network with an allowlist proxy; a non-root agent.

What we deliberately avoided

  • EmbodiedSWE imports the delivered solve.py into the grader process, and its wrapper blocks only reset and set_states, leaving the raw environment reachable. Here the delivered program shares neither a process nor a container with the environment or the verifier.
  • EmbodiedSWE writes the transcript into the agent-writable workspace. Here the launcher records the agent's output outside the container.
  • EmbodiedSWE grades with seed 0 by default, which may match the development start. Here grading seeds are drawn privately on the trusted side.
  • EmbodiedSWE's documentation says that not cheating is enforced "by prompt, not by access control". Here everything is enforced by access control.
  • Harbor runs submitted code on the verifier's filesystem and relies on deleting the sealed file, user nobody and seccomp. Here the delivered program never enters the environment side.
Does every random instance need a complete trajectory?

No. Use representative full witnesses, validate skill conditions, screen instances within budgets and generate local trajectories during execution. Screening passes, unknowns, failed checks and complete witnesses are distinct. Acceptance standard
