01 · 预算口径

主预算用仿真步数和 token，墙钟只作上限

“4 小时以上、不设上限”说的是任务的难度；评测时还需要一个能比较的预算口径。墙钟时间受硬件和负载影响很大：H1 在 GPU 被别的任务占用时，每个控制步要 0.67 s，同一个 agent 换一台机器、换一个时段，能做的实验次数就差好几倍。所以：

预算怎么计作用
仿真步数环境一侧计数：command 推进的控制步之和，reset 前后都算主预算：决定 agent 能做多少次物理实验
token可信侧代理独立计量的 LLM 输入、输出 token，以及折算的费用主预算：决定 agent 能思考多少
观测次数环境一侧计数防止无限制地读传感器
reset 次数开发模式下的上限防止靠反复重来代替理解
墙钟启动器计时只作上限，防止卡死；不用来比较
  • 任一主预算用完，开发会话结束。
  • 所有预算都由环境一侧或可信代理计量，agent 自己报的不算。
  • 各项额度写进每个任务的任务卡，并注明它们在参考硬件上大致对应的墙钟时间。

02 · 交付快照与按预算点评分

报告分数随预算怎么变化，而不只是一个最终分

  • 开发会话中，可信侧在几个预算点给工作目录拍快照，记下当时的预算用量。预算点按仿真步数和 token 定义，比如参考硬件上大约 4、12、24 小时对应的量。
  • 每个快照都在评分模式下、在密封的新回合上自动评分（每个回合 3 次，见第 04 节）。一次评测因此得到一条“分数—预算”曲线，3 次评测得到 3 条。
  • agent 不知道快照在什么时候拍；它只需要随时把当前最好的程序放在约定的入口（见隔离沙箱第 06 节）。
  • EmbodiedSWE 也会给每次提交的快照记下墙钟时间和对话位置；这里改用环境一侧计量的预算。

03 · 成绩怎么报告

每个任务、每一层分开报告，再汇总

报告项怎么算
原始分每个评分回合的过程分（进度峰值，3 次评分取平均），按回合平均
成功率每个评分回合是否成功（0 / 1，3 次评分取平均）的平均
归一化分原始分除以参考专家解的分（空操作为 0）。参考解没有覆盖全部阶段的任务，只报原始分
分层第 1、2、3 层分开报告，另给三层等权平均
跨任务汇总每个任务等权：归一化分（没有的用原始分）的平均、成功率的平均；不按回合数加权
阶段每个阶段的平均最好值，看 agent 卡在哪一步
重复3 次评测各自的分数、均值和范围；评分重跑 3 次之间的最大差别；不可复现的回合数
开销仿真步数、token 和费用、观测次数、reset 次数、墙钟
标记与无效被标记的回合数和原因；判无效的回合数

所有数字都来自自动评分；每份报告都注明任务版本和评分器版本（第 06 节）。

筛查账本与执行成绩分开

按 witnessed_full、screen_pass、unknown、rejected 分别报告数量、总抽样数、预算耗尽和拒绝原因。技能探测与完整执行另列分母，筛查通过不计任务成功或参考满分。自建候选集可按预声明规则筛选；基准预定样本全部保留，未知／失败不能静默移除或换 seed。若报告子集，必须同时给出完整抽样账本、预声明选择规则和各状态数量。原 agent 评测及评分重跑要求继续有效，不意味着先求出每个随机样本的完整参考解。

04 · 统计要求

回合数、重复 3 次和置信区间

  • 评分回合：建议每层至少 10 个密封回合，按任务类型分层抽样。回合太少，得分波动会很大（H1 沙箱的说明里也提到了这一点）。
  • 评测重复 3 次（硬性要求）：每个 agent 在每个任务上跑 3 次独立的评测，每次从新的开发会话开始。agent 自身的随机性往往比回合的随机性还大，单次评测代表不了能力。三次的分数都报告，再给均值和范围。
  • 评分重跑 3 次（硬性要求）：每个交付快照在同一批密封回合上自动评分 3 次。GPU 上的物理仿真不保证逐位重复，重跑检验评测输出能不能复现：三次的成功判定要一致，单回合得分差在容差内（比如 ≤0.05，具体写进任务卡）。回合得分取三次的平均。
  • 复现不了怎么办：三次评分差别超过容差的回合，自动标记为“不可复现”，仍取平均计分；这说明任务或评分器对物理波动不稳健，由维护者修，下个版本自动重评。
  • 置信区间：对回合和会话做自助法重采样，给出 95% 置信区间；两个 agent 的区间重叠时，不排先后。
  • 不挑最好：评分取平均，评测全部计入，不重跑挑最好。

回合数和容差是建议值，每个任务按自己的方差在任务卡里定下来；重复 3 次是硬性要求。都在评测前冻结。

05 · 基线

除了空操作和参考解，还要有标准 agent 基线

基线用途
空操作下锚点，必须得 0
参考专家解上锚点；证明可解、验证评分器
标准 agent 配置固定版本的 coding agent（比如 agent 镜像里可选安装、版本固定的 Claude Code）加默认提示词，在同样的预算下跑。给出难度和区分度的参照，并检验“强 agent 要 4 小时以上”这个假设
简单脚本基线（可选）只用任务提供的技能、不做感知的固定脚本。检验任务是不是靠固定套路就能拿分

基线结果随任务版本一起发布，任务改版后重跑。贡献流程里的难度试跑就用标准 agent 配置。

06 · 版本与可复现

每个成绩都能追溯到确定的版本

版本号和哈希

  • 任务版本 主版本.次版本：会改变评分结果的改动（场景、判据、阈值、权重、监视器规则、仿真设置、执行和感知的延迟）升主版本；只改文档升次版本。
  • 每个评分结果都记下：任务版本、评分器代码哈希、仿真器版本（如 Genesis 1.4.3）、素材哈希、agent 镜像的内容哈希、硬件，以及（只在可信侧）种子。

GPU 上的物理不确定性

GPU 上的物理仿真不保证逐位重复。评测时怎么重跑，见第 04 节；任务验收时怎么重跑，见任务验收第 03 节。

改版后自动重评

  • 可信侧保存所有交付快照。任务升主版本后，自动在新版本上重评全部快照；旧成绩保留，并标明版本。
  • 每个任务维护一份变更记录：改了什么、为什么（比如哪个被标记的回合暴露了什么问题）、对成绩有什么影响。

07 · 防泄露与对外公布

私有材料不出可信侧，对外只公布汇总

公开和私有

材料公开的开发任务私有的评测任务
指令、机器人和传感器规格、SDK公开公开（agent 本来就能拿到）
任务说明、设计文档公开只公开目标和类别，不公开要发现什么
参考专家解、官方轨迹可以公开私有
评分器代码、判据阈值、权重、反例集、监视器阈值可以公开私有
密封种子私有私有，每轮评测更换
任务检查记录、被标记的回合只给维护者只给维护者

防止进入训练数据

  • 私有材料只放在私有仓库或可信侧，不进任何公开仓库、网页或论文附录。robo-si 现在是私有仓库。
  • 每个任务文件里放一个 canary 字符串，用来检测训练数据有没有被污染；Terminal-Bench 的任务文件就带有这样的字符串，本地的 Harbor 任务里还没有。
  • agent 的网络只放行 LLM API（隔离沙箱第 03 节），评测时搜不到任务资料。

评测结束后对外公布什么

  • 公布：每个任务、每一层的原始分、归一化分、成功率、置信区间和开销；阶段平均最好值；被标记和判无效的回合数；任务和评分器版本。
  • 不公布（私有任务）：逐回合的录像和日志、判据细节、密封种子、交付程序和对话记录。公布这些，下一轮就可以针对评分器过拟合。
  • 公开的开发任务可以公布逐回合的录像和日志。
  • 会话中 agent 能拿到哪些反馈、哪些只留在可信侧，见隔离沙箱第 05 节。
