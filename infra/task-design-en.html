Task design guide

Get the task design right
before writing any code.

The first step of contributing: how to design a new task. The eleven hard requirements are expanded one by one, ending with a design self-check and the task card template. The reference expert solution and feasibility verification are on the task acceptance page.

01 · Eleven hard requirements

The task card must address every one

  1. Several interactive objects, no direct instruction. The scene has several objects that can be pushed, carried, placed, stood on or connected; the instruction gives only the goal and the public validity constraints. Section 02
  2. Establish feasibility evidence in layers. A few complete references witness declared configurations; validate skill conditions, screen random instances within budgets and generate local trajectories only for execution. No full solution per random instance is required. Review and independently reproduce representative evidence. Section 03 of task acceptance
  3. The final goal involves at least one capability class: tool use or reaching a precondition; complex interaction, torque or WBC computation; a non-intuitive solution. Section 02
  4. Terminal-Bench-style difficulty. A strong coding agent needs more than 4 hours of iteration; solving time has no upper limit. Section 02
  5. Only sensors native to or mountable on the robot; no cheating. No spatial coordinates, object poses, physical properties, segmentation or purposes. Section 08
  6. Consider corner cases. Shortcuts around the point of the task are ruled out at design time; remaining reasonable unconventional solutions are scored automatically by the states they reach. Section 07
  7. Strictly prevent bypasses and reward hacking. Distrust by default; an attack list, negative cases for every stage, exploit tests; grading is automatic, and people check the task and its verifier on video at admission. Section 09
  8. Initial states as random as possible. Declare random ranges and screening states; valid generated geometry is not a solvability claim. Check shortcuts and ensure the solution is not knowable only from ground truth. Section 04
  9. Exactly three difficulty layers, each building on the one below. Necessary tools only → plus tools only another body could use → plus distractors. Section 05
  10. Decomposable into subtasks, keeping curriculum learning possible. Subtasks have completion conditions stated as states, and start states from which they can run on their own. Section 06
  11. Built on Genesis / Isaac Lab, preferring official and fine-grained asset libraries. Official robot models; for objects, simulator-official assets and part-level asset libraries with physical properties first. Section 03

Remaining work for 12 tasks: selected full witnesses, low-level actions and trajectory mappings

Minimum design-feasibility evidence: demonstrated high-level plan → low-level action plan → actual trajectory mappings, plus at least one generated, continuously successful end-to-end expert trajectory. For example, refine getting onto a box into weight transfer, successive foot lifts and support establishment, then bind actions to trajectory segments. This is an existential witness in a declared configuration, not a guarantee over arbitrary random states, arbitrary skill composition or a requirement to finish a general rolling planner. Existing full trajectories may be reused after checking provenance and mappings; broader applicability is separate. Representation refinement requirements

02 · Scene, goal and instruction

Several interactive objects, a clear goal, no route

Covers R1, R3, R4.

Interactive objects (R1)

  • The scene has several objects that can be pushed, carried, placed, stood on, connected, wedged or levered. A scene with one object whose use is obvious does not qualify.
  • Objects are of three kinds: necessary tools, tools this robot cannot use but another body could, and distractors. The difficulty layer decides which appear (section 05).
  • What an object can do must be discoverable by experiment: push it, lift it, try standing on it, and see the result in the sensors.

Writing the instruction (R1)

The instruction gives the goal and the public validity constraints only. Objects get neutral names (colour, number); no purpose, no route or steps, and no verbs that imply a method ("stack", "climb", "pry", "wedge").

StyleExampleVerdict
Goal only"Put the red box in the green goal area on the floor."Fine
Public validity constraint"The box must never rest on a step while being carried."Fine a constraint is a rule, not a hint
Purpose and route"Stand on a floor box to take the red box down."Not allowed
Steps"First wedge the door, then carry the box through."Not allowed
Names that imply use"step box", "wedge", "lever"Not allowed use "brown box", "object A"

Capability classes of the final goal (R3)

At least one, possibly several:

ClassMeaningExamples in the current tasks
Tools / preconditionsAn object must first change the environment, or a state must first be reached, before the goal is possible.H1 standing on a box; H2 moving a heavy load with a cart; H3 dual-robot door holding or independent heavy-crate support
Complex interaction / torque / WBCWhole-body coordination, balance under load, torque computation or cooperative force.H6 carrying a box upstairs; H5 levering a heavy box; M2 two robots carrying a long box
Non-intuitive solutionThe direct approach must fail and a change of approach is needed, or there are apparently useful traps.H1's tall narrow distractor; M3 using the other robot as a tool

Difficulty (R4)

  • Aim for a task a strong coding agent needs more than 4 hours of iteration to solve. Solving time has no upper limit; time and tokens are recorded and reported.
  • Difficulty comes from: dependency depth, tool composition, failures that need recovery, estimating geometry from depth and point clouds, and judging the robot's own capability.
  • Difficulty should not come from: visual clutter, repetition, precision for its own sake, or information available only as ground truth.
  • "Long horizon" means dependency depth, tool composition, persistent state and recovery, not video length (v5 section 10).
  • If the difficulty pilot solves it too quickly, deepen dependencies (more preconditions, property changes), widen the random ranges, or use distractors that are harder to tell apart.

Solvable and infeasible episodes

A task may include deliberately infeasible episodes (such as H1's infeasible family), in which the agent must call declare_infeasible. "Infeasible" needs a declared validation scope (which approaches were tried and why none can work), never one agent's failure (v5 section 11). Declaring a solvable episode infeasible is flagged.

Multi-robot tasks

First test whether one robot can do it alone, and separate "cooperation required" from "cooperation only saves effort". Two robots in a scene do not make a cooperation task; if one robot can do it, change the label or adjust length, mass or towing force until it cannot (v5 section 9).

03 · Simulators and assets

Genesis / Isaac Lab, official robot models, official and fine-grained asset libraries first

Covers R11.

Simulator backends

  • Genesis first. The sandbox's trusted worker runs Genesis (currently 1.4.3). Every new task needs at least a Genesis backend.
  • Isaac Lab parity is recommended (the local setup is Isaac Sim 5.1 + Isaac Lab 2.3.2). Both backends share one task core (TaskCore): the same seed and episode index give exactly the same scene. H1, H2 and historical single-G1 H3 have both backends; current dual-G1 H3 and H6 are verified in Genesis only.
  • Parity needs consistency checks. Run the same commands in both backends and compare object trajectories, contacts and predicate results; record differences and their causes in the task README.
  • Fix the simulation settings in the task card. Time step, substeps, solver, contact parameters, self-collision; none can change in evaluation.
  • State backend limitations. For example, Genesis 1.4.3 has no ray sensor, so H1's MID-360 LiDAR is assembled from four depth cameras and scans a regular grid.

Robot models: use the official ones

  • G1: MuJoCo Menagerie's unitree_g1 (BSD-3-Clause), downloaded at a pinned commit by setup_assets.py; sensor mounts come from Unitree's official URDF.
  • Go1 / Go2: Unitree's official or MuJoCo Menagerie's models; Isaac Lab ships configurations for Unitree robots.
  • Do not quietly change the model's masses, torque limits or joint limits. Body parameters that should vary (strength, payload) are randomised explicitly in the task, with public ranges.

Object assets: choose by priority

PrioritySourceGood forExamples in the current tasks
1Simulator-official assets: the Isaac Sim asset library, Genesis's built-in assetsCarts, shelving, industrial objects; usually with collision and physics propertiesH2's cart (NVIDIA Dolly)
2Fine-grained asset libraries: part-level libraries with joints or measured properties, such as PartNet-Mobility (SAPIEN; articulated cabinets, doors, drawers), Google Scanned Objects, the YCB object setArticulated furniture and appliances, everyday objects the hands can manipulateNot used by any task yet
3High-quality CC0 models: Poly HavenFurniture, crates, floor and wall texturesH1's cabinets and folding stool; H2's and H3's crates and shelving
4Self-built geometryWhen no suitable asset exists, or dimensions must be controlled exactly (such as step heights)H1's floor boxes

Using level 4 needs a reason in the task card for why levels 1–3 do not fit. Licences differ between libraries; check and record each one.

Asset requirements

  • Source and licence: record each asset's source URL, author, licence and modifications (see H2's asset_sources.json). Assets whose licence forbids redistribution stay out of git and are downloaded by script.
  • Reproducible: download scripts pin versions and check hashes (H2 records SHA-256; Poly Haven downloads check the MD5 the API provides).
  • Real-world scale: scale to real dimensions and record what was scaled.
  • Collision matches visuals: collision proxies are simplified boxes or convex decompositions that match the visual mesh closely enough. The agent sees the visual mesh through RGB-D while physics uses the collision proxy; a mismatch is a trap for the agent and a possible exploit.
  • Realistic physics: mass, friction, centre of mass, inertia, and for articulated objects damping, limits and spring force, all within real ranges and randomised per section 05.
  • One asset for both backends: after URDF / MJCF ↔ USD conversion, check geometry, masses and joint parameters.
  • Appearance reveals no purpose: no "STEP" or "TOOL" lettering or special marks. Colours may identify the target but must not hint at uses.
  • "Unusable" must be physically unusable: not load-bearing, collapsing, fixed to the floor: all implemented in simulation (weak joints, low stiffness, fixed constraints and so on), never by a predicate that says "using it does not count".
  • Affordable rendering: texture resolution sufficient for RGB perception (current tasks use 1K).

04 · Initial-state randomisation

Randomise everything that can be; no fixed start or layout

Covers R8.

A private seed decides every episode. Randomisation makes hard-coded layouts worthless, forces the agent to rely on perception and closed-loop control, and gives multi-episode grading statistical meaning.

What to randomise

CategoryVariablesWhat H1 does now
Robot startPosition, headingNominal start ±0.15 m, heading ±0.3 rad
Object setWhich objects appear, how many2–4 coloured boxes on the cabinet; floor boxes required by the family, the others each present with 50% probability
Object posesPositions, orientationsFloor boxes on 8 candidate spots with ±0.1 m jitter, yaw ±0.4 rad
TargetWhich object, whereRandom target colour, level and slot
FurnitureModel, size, shelf heights3 cabinet models, two shelf layouts each
Physical propertiesMass, friction, centre of massFloor-box masses 1–15 kg depending on the box, friction 0.3–0.8; in 30% of episodes the medium box is light and slippery
Body parametersStrength, payload (within public ranges)Leg and arm torque limits ×0.85–1.0, 0–5 kg on the torso
SensorsNoiseIMU noise taken from the MJCF

Three constraints

  1. Label instances by evidence. Samples follow the declared layer and generation rules. Distinguish complete witnesses, screening passes, unknowns and failed checks. No full solution per draw is required; failure to find a solution is not proof of physical infeasibility.
  2. Open no shortcut. No corner of the random ranges may allow a solution that bypasses the point of the task, such as a shelf drawn so low that it can be reached on tiptoe. Test the edges of the ranges with oracle samples (section 03 of task acceptance).
  3. Nothing essential known only from ground truth. Randomised hidden properties must be inferable from robot sensors: how hard a push is, whether a box wobbles when stood on, joint torques while lifting.

Seeds and splits

  • Counter-based random numbers keyed by (seed, environment index, episode index): an episode is identical in both backends and on every re-run.
  • In evaluation and grading, seeds are drawn privately on the trusted side; the agent never sees them.
  • Development and evaluation use different seed sets; grading is stratified by difficulty layer (and family).

Writing the generator

  • Draw positions and properties for every candidate object first, then let the difficulty layer decide which are present (section 05). The necessary tools are then identical across the three layers for one seed.
  • Samples that violate the constraints (overlaps, unreachable, outside the layer definition) are rejected; the rules go into the task card and the rejection rate is recorded, so the distribution is not silently skewed.
  • Subtask start states come from the same generator (or checkpoint restore) and are randomised as well (section 06).

What not to randomise

The robot model and hardware limits (apart from body parameters within public ranges), the instruction template, the public validity constraints and thresholds, and the simulation settings.

05 · Three difficulty layers

Exactly three layers, each building on the one below

Covers R9.

LayerWhat the scene containsWhat it testsWhat the designer states and verifies
Layer 1
Necessary tools only		The goal, plus the tools and objects the task needs, and nothing else.Discovering what the objects can do and how they combine, and executing it.Why each object is necessary: without any one of them the task cannot be done (verified with the oracle).
Layer 2
Tools this robot cannot use		Layer 1, plus tools or objects this robot cannot use but a different body could.The agent's model of its own body: height, leg length, step height, hand size and grasp width, joint torques, payload, foot area.For each object, which body could use it (a taller humanoid, a quadruped such as Go1, a different hand) and why this robot cannot, even combined with other objects (if a combination works, it is another route, handled under R6); the oracle confirms this robot really cannot use it.
Layer 3
Distractors		Layer 2, plus distractors: objects or tools beyond this robot's capability (too heavy, too tall, too large, too narrow), and objects that do not actually work (not load-bearing, tipping when stepped on, fixed to the floor, hollow and collapsing, a handle that is only decoration).Ruling out apparently useful options: experimenting to collect evidence, and changing route after failure.Why each distractor cannot be used, and from which sensor reading the robot can find this out before committing to it; never knowable only from ground truth.

Rules

  • Cumulative, one seed. The goal, the necessary tools and their positions are the same in all three layers; a higher layer only adds objects. Score differences can then be attributed to recognising tools the robot cannot use and to ruling out distractors.
  • Evidence for each declared layer. Added objects may obstruct routes or introduce shortcuts. Select complete representative references for each declared layer/variant, alongside skill and instance screening; do not require full execution of every random draw. List deferred layers explicitly (acceptance section 03).
  • Added objects go into the corner-case list. They may be put to unexpected uses (section 07).
  • The agent is not told the layer. Knowing it is layer 1 means knowing every object is useful. Results are reported per layer.
  • Layer 2 versus layer 3. Every layer-2 object names a body that could complete the task with it, and tests self-modelling; layer-3 distractors need no such body, and test experimenting, collecting evidence and ruling options out.
  • Relation to v5. These three layers replace the v5 L0–L2 curriculum: apparently useful traps belong to layer 3 and need obtainable evidence; property changes, faults and noise belong to the initial-state randomisation. Capability disclosure (explicit / partial / latent) is an independent axis, not a difficulty layer.

Example: H1 scenes that need one support

LayerWhat stands on the floor
Layer 1A single low box that is high enough.
Layer 2Plus a box of the right height that is too heavy for the G1 to push, placed far from the cabinet (a stronger robot could move it).
Layer 3Plus the tall narrow box (too tall to climb, too narrow to stand on) and a hollow box that collapses when stepped on (not implemented).

06 · Subtasks and curriculum

Decomposable, runnable on their own, keeping curriculum learning possible

Covers R10.

Design the task as a dependency chain of subtasks. Each subtask has two things:

  • A completion condition stated as a state. For example "a box that can be stood on rests in front of the cabinet", not "push the box". Different methods can then satisfy it, and no single route is prescribed. Subtasks map one to one onto the process-scoring stages (section 09).
  • Start states from which it can run on its own: the states after all earlier subtasks are complete. Either the trusted side restores them from checkpoints recorded in oracle runs (the H1 sandbox supports this: world parameters and a full-body snapshot are restored, and the replay matches exactly), or the generator places a physically valid state and lets it settle (no interpenetration, nothing floating), randomised as well.

Example: H1's subtask chain

1 Support in placeA usable box stands upright and at rest in the placement zone for 1 s (front face ≤0.15 m from the cabinet, lateral offset from the target ≤0.30 m)The task's initial statesupport_placed

H1's tool_engaged (a box was handled) is behavioural evidence rather than a state; it is an auxiliary process stage, not a subtask of its own.

Two curriculum axes

  • Difficulty layer: layer 1 → layer 2 → layer 3.
  • Subtask start: from last to first; practise the last step, then lengthen the chain.

Who may use subtask scenarios

  • A subtask start state reveals the route (for example "the box already stands in front of the cabinet"), which amounts to an instruction. Subtask scenarios are therefore for training, diagnosis and analysis only, and never offered to the agent under evaluation.
  • Evaluation always starts from the task's initial state; the trusted side alone decides start states and layers by the evaluation plan.
  • A future curriculum track that uses subtask scenarios is reported separately, never mixed into the main leaderboard.

07 · Corner cases

Rule out shortcuts; credit reasonable unconventional solutions

Covers R6.

Procedure

  1. List every unconventional route. Including the direct approach a taller or stronger body would take, other uses of distractors, using furniture, one robot instead of cooperation, corners of the random ranges, and new routes the objects added in higher layers allow.
  2. Classify. A shortcut around the point of the task (making the tool, the precondition or the cooperation unnecessary), or a reasonable unconventional solution.
  3. Rule out shortcuts. Constrain disallowed routes through geometry, mass, friction, layout or body parameters, with necessary-condition counterexamples or targeted physical evidence. One failed search or attempt does not prove every alternative impossible; state the validation scope (acceptance section 03).
  4. What cannot be ruled out physically goes into the public constraints. For example "keep holding the box; never rest it on a step".
  5. The rest are scored automatically. Predicates read states and prescribe no route, so an unconventional solution that executes continuously in physics, obeys the public constraints and passes every integrity check earns the stages whose states it reaches; skipped intermediate stages are never back-filled. The design must make sure reasonable unconventional solutions pass through these states.
  6. A shortcut that slipped through. If flagged episodes in evaluation reveal a shortcut that should have been ruled out, it is recorded as a design defect and fixed in the next version, and every agent is re-graded automatically on that version.
Exploits are not solutions: penetration, teleporting, energy anomalies, state edits and predicate gaming are invalid (section 09).

Only sensors native to or mountable on the robot

Covers R5.

RobotNative (per Unitree's specifications)Mountable

Declare every sensor's model, mount pose, field of view, resolution, rate, range and noise; for mountable sensors, where they are mounted. A task may disable sensors, but missing sensors and degraded signals are recorded separately.

What the agent gets and never gets, the action channel (one LowCmd-style command per joint, clipped to hardware limits), the L1–L3, VLA and IK/FK tools, and the skill interface are provided by the sandbox for every task; see section 03 of the isolated sandbox and section 04 of the isolated sandbox. The task card states:

  • Which tools the agent may use (L1, L2, L3, VLA, IK/FK).
  • Which skills are provided (possibly none) and why they do not give away the route; skills and rollouts the agent produces itself are the preferred references.
  • Capabilities the task needs but no executor provides (stepping up, grasping) are blockers, never filled by a hidden task macro (v5 section 18).

09 · Scoring and protection material

What the design fixes for scoring

Covers R7. The scoring, automatic scoring rules and bypass defences are described in scoring and verification; the delivery format is the submission checklist on the home page.

  • Stage predicates: one per subtask (section 06), written as described in section 03 of scoring and verification.
  • Weights and values: a continuous 0–1 value and a weight per stage.
  • Attack list and negative cases: the task's attack list by the seven attack categories, and a set of must-not-score negative cases per predicate (section 08 of scoring and verification).
  • Monitor thresholds: thresholds for each kind of alarm; how alarms are handled is a common rule (section 05 of scoring and verification).
  • Human check list: what the three questions mean for this task, used when a person watches videos at task acceptance (section 05 of task acceptance).

10 · Design self-check

Answer every question before submitting the task card

Scene and instruction

  • Given only the goal, why does the most direct approach certainly fail?
  • Is the task still solvable without each object? If so, it does not belong to layer 1; classify it as layer 2 or layer 3.
  • Read the instruction aloud: does any word hint at an object's use or a route?
  • How many ideas and failures would the strongest agent go through? If it would take less than 4 hours, where does more difficulty come from?

Simulation and assets

  • Is every asset's source, licence and hash recorded? Why was no higher-priority asset used?
  • Do collision shapes match the visuals? Are physical properties within real ranges?
  • Are "unusable" objects really physically unusable?
  • Do both backends produce the same scene and results for the same episode?

Randomisation, layers, subtasks

  • What full, skill or screening evidence covers boundary and interior samples? Are unknown ranges explicit? Does any corner open a shortcut?
  • For each layer-2 object: which body could use it? Why can this robot not, even combined with other objects?
  • For each layer-3 distractor: from which sensor reading can the robot tell it is unusable before committing to it?
  • Can every subtask start from its own start states and be judged on its own? Is its completion condition a state or an action?

Solvability, acceptance, bypasses

  • From which sensor readings can the agent infer that an object bears load, moves, or is tall enough?
  • Does each declared layer/variant have preselected complete representative witnesses? Are skill conditions and actual transitions evidenced? Have the required representative videos been reviewed?
  • List every alternative solution you can think of: which bypass the point of the task and must be made impossible, and which are reasonable and earn credit?
  • Read every stage predicate as an attacker: can it be scored without really completing that step?
  • Does the verifier judge the reference expert successful and a no-op 0?
  • Can a person watching the reference and exploit-test videos answer the three questions with your check list?
