Task infrastructure · Isolated sandbox

The agent only sees its sensors;
scoring stays on the environment side.

Every task is evaluated in the same kind of isolated sandbox, modelled on Terminal-Bench (the Harbor format) and EmbodiedSWE. This page sets out the sandbox's four requirements and implementation principles. The H1 sandbox is the reference implementation (H1 sandbox README); its progress is on the implementation status page. The verifier, monitors and fabrication checks are on scoring and verification.

01 · Four requirements

What the sandbox must guarantee

RequirementDetails
1 Agent and environment are isolated. The agent gets only the robot's RGB / LiDAR and other onboard sensors, and is strictly cut off from everything else; it decides and chooses actions itself; it may call the L1–L3 solvers and tools such as VLA or IK/FK (where the task allows), using only its own sensor results; it may use designated skills through the skill interface, preferably skills and rollouts it produced itself; or it may plan trajectories with its own coding ability.Section 03
2 The environment executes actions; the world cannot be edited. The agent can never force changes to the environment (object positions, sizes, masses, friction and so on).Section 04
3 A reference expert solution and the official trajectories. A reference expert solution (the existing expert, which reads ground truth and plans with IK/FK) proves the problem is solvable and validates the verifier; official trajectories are kept, may use the current settings and be split into subgoals; the agent may never use these privileged settings.Section 01 of task acceptance
4 The verifier is isolated from the agent and cannot be hacked. At minimum, verification and scoring are kept apart from the agent; scoring is by stage; monitors guard against reward hacking and against the agent fabricating outputs or inputs.Section 02 of scoring and verification; scoring and verification

02 · Structure and lifecycle

Two sides, one channel, one control pipe

agent container (Linux; uid 1000, read-only root, all capabilities dropped, internal network)
  /opt/g1sandbox  read-only: SDK, L1 weights, L2/L3 solvers, robot model, examples
  /workspace      the only writable directory (a fresh copy per graded episode)
        |  RPC: token auth, length-prefixed JSON, no pickle, 8 whitelisted methods
        |  only exit: socat forwarder -> environment port (optional: squid allowlist -> LLM API)
        v
environment side (trusted; an env container on a Linux server, a worker process on the Windows host here)
  world        built from a sealed scene before the agent connects; no way to edit it afterwards
  sensors      mounted on the robot only: RGB-D, LiDAR, IMU, joints, hand and foot contact forces
  limits       commands validated and clipped to joint, velocity, gain and torque limits
  recorder     privileged state log, per-object contacts, full-body snapshots, top-down video, request log
  monitors     interface, world integrity, physical anomalies, command patterns, predicate anomalies, resources
  verifier     reads only the records above -> verdict.json
        ^
        |  control pipe (the worker's stdin, held only by the launcher): next episode / shut down
launcher (trusted): builds the scene, issues the token, starts the agent container,
                    records the agent's output outside the container, re-runs the delivered program per episode

Deploying the environment side

Two deployments give the same isolation: on this machine (a Windows workstation) the environment side is a trusted worker process on the host, because Genesis and Isaac rendering only get llvmpipe inside WSL2 containers; on a Linux GPU server the whole environment side can also run as its own env container. The verifier lives on the environment side too; see section 02 of scoring and verification.

Lifecycle of one evaluation

  1. Development session. The launcher builds and seals the scene from a private seed, then starts the agent container. The agent iterates in development mode and may reset a limited number of times to the same sealed initial state.Recorded: request log, state log, video, agent output.
  2. Delivery. The agent leaves a control program in its workspace that only calls the SDK.
  3. Graded episodes. The trusted side draws N new episodes from private seeds. In each, the delivered program runs once from a fresh copy of the workspace in a new agent container (no LLM, no reset, a wall-clock budget). Only after the program ends does the launcher signal the next episode over the control pipe; an episode that never ran scores 0.
  4. Automatic verdict. The verifier reads the environment-side records and monitor alarms, gives every episode its stage credits, success and void status, and aggregates.
  5. Result. The automatic verdict is the final result; flagged episodes are collected for the task maintainers. The human check is for the task and happens when it is admitted (see section 05 of task acceptance).

03 · Isolation and perception

Requirement 1: the agent gets only the robot's own sensors

The agent container

  • User uid 1000, read-only root filesystem, --cap-drop ALL, no-new-privileges, process, memory and CPU limits.
  • Only two things are mounted: the read-only bundle built into the image (SDK, L1 weights, L2/L3 solvers, robot model, examples) and the writable /workspace.
  • Bundles and images are named by content hash; a static test checks that the bundle contains only these items and no trusted code, scenes, logs or reference solutions.
  • The network is --internal: the only exit is a socat forwarder to the environment port; when an LLM is needed, squid allows only the LLM API's domain.

What the agent gets and never gets is in section 05.

Sensor mounts come from the robot's official model (for the G1, Unitree's official URDF). A scene may disable a sensor, but joint proprioception cannot be disabled. Sensors the simulator lacks must be emulated and documented: Genesis 1.4.3 has no ray sensor, so the LiDAR is assembled from four depth cameras.

Decisions and actions: call tools, or write your own

LevelWhat it isInputs
L1GR00T WBC: standing and walking policies; given a body-frame velocity command and pelvis height, they output leg and waist joint targetsPelvis IMU and joint readings; no base linear velocity, no world coordinates
L2Target-point trajectory planning: IK on the robot's own model, then collision-checked interpolation or RRTCurrent joint angles, IMU attitude; obstacles estimated by the agent from depth or LiDAR and added to the model
L3Intermediate points with brute-force IK/FK: the agent supplies waypoints, solved segment by segment and joinedAs L2

Own codeThe coding agent writes its own perception, planning and control and sends joint commands directlyThe same: sensor readings and the robot model only

Partly allowed, own sensors only. Each task declares in its task card which tools are allowed (L1, L2, L3, VLA, IK/FK); tools that are not allowed are left out of the bundle, and the agent may still write its own. Allowed tools run on the agent side, where no ground truth exists, so their only inputs are the agent's own sensor readings and the robot model; this is enforced by structure, not by rules. Tools give the agent no extra information or privileges, and there are no task-specific primitives. The reference expert solution may read ground truth (section 01 of task acceptance); the agent may not.

Skill interface: designated skills only, preferably the agent's own

Task execution keeps a skill interface: the agent may use skills, or none at all. Usable skills come from only two sources, both designated in advance:

SourceWhat it isHow it is designated
Provided by the taskSkills listed in the task card, such as L1 standing and walking, plus execution helpers such as trajectory tracking and posture holding. No task-specific macros, nothing that gives away the routeListed in the task card, built into the bundle and hashed by content; anything not listed stays out of the bundle
Produced by the agent (preferred)Skills the agent writes and tunes itself during development, and the rollouts it ran itself (observation and command sequences) as references for them: replaying keyframes with closed-loop correction, fitting parameters, training small models offline and so onKept in the workspace and registered in a manifest: skill name, entry point, code hash, which rollouts it references; every rollout carries the observation digests issued by the environment, which prove where it came from
  • Not allowed. The reference expert solution and official trajectories (including their recordings), other agents' outputs, pretrained policies downloaded from the internet, task-specific macros. Network isolation and the bundle manifest block most of these by structure; the provenance check covers the rest.
  • Provenance check. The environment side records a digest of every observation in the hash-chained request log. The agent's rollouts reference these digests; before scoring, the trusted side checks every rollout in the manifest against the log to confirm it came from this agent's own development sessions. Anything that does not match is recorded as a fabricated rollout and voids the run automatically.
  • At grading. The delivered program ships with its skill library and rollouts; every graded episode gets a fresh copy, and nothing written during one graded episode reaches the next. Initial states are random, so rollouts can only serve as references; plain replay scores nothing.
  • Reporting. Results state which skills the delivered program registered and where each came from (provided by the task / produced by the agent).

04 · The environment acts; the world cannot be edited

Requirement 2: there is no way in to change the world

The agent can call only eight methods: info, status, observe, command, command_sequence, declare_infeasible, finish, and reset in development mode only. What each returns is in section 05.

Unknown methods, wrong tokens and malformed frames are refused, recorded as violations, and void the whole run (VOID). The worker serves one session at a time.

How commands are handled

  • One command per joint (mode, q, dq, kp, kd, tau, following Unitree LowCmd): motor mode recomputes PD plus feed-forward torque every physics substep; servo mode uses the simulator's implicit PD.
  • Non-finite values, wrong shapes and extra fields are refused.
  • q is clipped to joint limits, dq to velocity limits, kp / kd to gain limits, tau to nominal torque; the applied torque is further clipped to this episode's actual limit (including an undisclosed strength factor).
  • The simulation advances only during command calls; the agent's thinking costs no simulated time.

What does not exist

  • Any method that sets an object's position, orientation, size, mass or friction.
  • External base forces, attaching objects to the hands, changing gravity, the time step or physics options.
  • Resetting to an arbitrary state; there is no reset in evaluation or grading.

Integrity checks

  • The scene is built from a sealed scene file before the agent connects; connecting before sealing voids the run.
  • Masses and friction of all rigid bodies are hash-checked every 500 control steps; any change voids the run.
  • The verifier detects teleports (a displacement between two control steps implying >20 m/s).
  • Escape probes (36 for H1) try to break out from inside the container as the agent; all behave as expected, 17 are recorded as violations and the run is VOID.

05 · Feedback: to the agent, and private

The environment container gives only what the robot itself can sense

Feedback has three tiers: what the agent gets over RPC during a session; what stays on the environment side and the agent never gets; and what is published after an evaluation. The principle: feedback to the agent is what a real robot could also get; nothing related to scoring is given.

1 Feedback to the agent (during the session, over RPC)

SourceWhat it gives
infoThe instruction; capability information per disclosure tier; budgets (simulated time, observations, resets, steps per call); robot specification (joint names, limits, velocity and torque limits, gain limits, control period, the two command modes); sensor specifications
observeOnboard sensor readings: joints, IMUs, RGB-D, LiDAR, hand and foot contact forces; each call uses one observation from the budget
command / command_sequenceProprioception after execution (optionally per step) and status; how many values per field were clipped to the nominal limits. The applied torque is in the joints' tau_est, so the agent can discover this episode's actual strength limit, as on a real robot
statusSimulated time, simulated time left, observations and resets left, whether the episode is over and why (finished, declared infeasible, fallen, time limit, reset, closed)
ErrorsInvalid parameters: the error type and reason, with no world information. Internal environment errors: only "internal error (logged on the trusted side)"
Out-of-bounds requestsUnknown methods, wrong tokens, malformed frames: a bare refusal, recorded as a violation on the trusted side; the agent is not told that the run is now void
reset (development mode only)Back to this episode's sealed initial state, a limited number of times

2 Private feedback (environment side only)

Used only for scoring, task checks and maintenance; the agent never gets it, during or after the session:

  • The privileged state log: object poses and velocities at every control step, contact forces per object split into hand, foot and other; 10 Hz full-body snapshots.
  • The top-down video.
  • The request log: every call, clipping records, violations (later with a hash chain and observation digests).
  • Monitor alarms and flags.
  • Scoring results: automatic score, stage timelines, success, void status and reasons.
  • Rollout provenance results, task check records, sealed seeds, reference solutions and recordings.

3 What is published after an evaluation

Aggregate results, cost and versions; for private tasks no per-episode videos, logs or predicate details. Details in section 07 of the evaluation protocol.

Feedback deliberately withheld

  • Scores, stage progress, success, intermediate predicate states; not even after finish().
  • Monitor alarms, flags, void status.
  • Object poses, sizes, masses, friction; the difficulty layer; seeds; whether a declaration of infeasibility was right.

Why: judging whether the task is done is itself part of what is tested, and the agent has to verify it with its own sensors; a success signal would let it probe the verifier until the signal flips. For comparison, EmbodiedSWE feeds the scene's own success check back to the agent during development, while Terminal-Bench shows no test results. Any extra feedback such as a success signal can only be a separate track: rate-limited, reported separately and never mixed into the main leaderboard.

07 · Multiple robots and realistic execution

Two things new tasks will need that do not exist yet

Multi-robot tasks (M1–M4)

  • Default: one agent, one session, several robots. Commands and observations are namespaced per robot, and each robot gets only its own onboard sensors. This keeps the test about one coding agent and is the simplest.
  • Optional: one agent per robot. Each agent has its own session and token and only its own robot's sensors; agents talk only through a message channel provided by the environment, logged on the trusted side, with bandwidth and latency stated in the task card. Reported as a separate track.
  • The need for cooperation is verified first, as the task design guide requires: one robot alone cannot do it.

Realistic actuation and sensing

  • Today commands take effect synchronously and immediately at the 50 Hz control step; the IMU comes from finite differences plus noise; cameras and LiDAR have no latency.
  • Suggested: control latency and jitter, occasional dropped commands, sensor latency and timestamps, randomised per episode within public ranges (section 04 of the task design guide), so programs written in simulation are closer to what a real robot needs.
  • These are simulation settings of the task: stated in the task card, fixed during evaluation, and changing them bumps the task's major version (section 06 of the evaluation protocol).
