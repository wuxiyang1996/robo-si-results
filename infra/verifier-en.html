02 · Where the verifier lives and what it reads

The floor: verification and scoring are isolated from the agent

How far the isolation goes

  • The floor: verification and scoring are isolated from the agent, which cannot read, change or influence them. This sandbox puts them on the environment side.
  • The verifier, stage predicates, scoring code, sealed episode seeds, anchors, reference solutions and recordings exist only on the environment side, never in the agent's bundle, image or workspace.
  • The delivered program always runs in an agent container and talks to the environment only over RPC; it never enters the environment side. This is stricter than Harbor (submitted code runs on the verifier's filesystem) and EmbodiedSWE (submitted code shares the grader's process).
  • Results (verdict.json) are written to the trusted directory on the environment side; the agent gets no score during the session, and finish() does not report success.

What the verifier reads

Only records written by the environment side: the sealed scene file, the privileged state log (every control step, including contact forces per object split into hand, foot and other), full-body snapshots, episode events, the request log and monitor alarms. Anything the agent writes can show up only through these records; the verifier never reads the agent's workspace, output or claims.

Fail closed

  • An episode that never ran (crash, no connection, timeout) scores 0.
  • A verifier error, missing or corrupt records, or a result that is not finite or outside [0, 1]: the episode scores 0 with the reason recorded, following Harbor's test.sh.
  • Any failed integrity check: the whole run is void (VOID) and scores 0.

The two deployments (a host process on this machine / a separate env container on Linux) are described in section 02 of the isolated sandbox.

03 · Stage predicates

Predicates read only physical state, never a single frame

Stage predicates

  • Stages map one to one onto subtasks (see section 06 of the task design guide); predicates read only the trusted state log, never what the agent says or which method it used.
  • Every predicate requires contact evidence, object identity, a dwell time and rest conditions; no single-frame triggers.
  • Distance-only predicates are paired with contact or motion evidence. (H1's target_reached currently accepts "hand within 0.15 m of the target centre" and does not meet this rule; it needs fixing.)
  • Every predicate has a set of negative cases (section 08), all of which must score nothing.
  • Thresholds are calibrated on the reference timeline and the manual labels (see section 03 of task acceptance), and frozen before evaluation.

04 · Scoring and grading mode

Continuous stage credit, re-run on sealed new episodes

Scoring rules

  • Each stage has a continuous 0–1 value at every control step: how much of it has been done.
  • Two modes: once milestones keep their best value so far; live stages count their current value (the score drops if the target is knocked out of the goal).
  • progress(t) = Σ weight × value(t) / Σ weight; the episode score is the peak of progress over the episode.
  • Success (0/1) is reported separately, as in Terminal-Bench.
  • Stages that cannot be earned in this episode (judged from the initial state only) are dropped and the weights renormalised.
  • A fall or a declaration ends the episode and earlier progress is kept; declaring a solvable episode infeasible is flagged.
  • A void run (VOID) scores 0.

Grading mode and reporting

  • Official results come from re-running the delivered program on N sealed new episodes, not from the development session; every episode is scored 3 times and averaged, and the whole evaluation is repeated 3 times (see section 04 of the evaluation protocol).
  • What is reported and how it is aggregated: section 03 of the evaluation protocol.

H1's stages, weights and values are in sections 5.3–5.6 of the H1 sandbox README; the weights have not yet been calibrated on real agent results.

05 · Automatic scoring rules

Grading agents is fully automatic; alarms follow fixed rules

When agents are evaluated, nobody watches videos or edits scores: the verifier's verdict is the score, and every kind of alarm is handled by the table below. The human check is only for the task, at acceptance (section 05 of task acceptance).

SituationAutomatic handling
Integrity alarms: out-of-bounds requests, changed world parameters, teleports, connecting before the scene is sealedThe whole run is void (VOID) and scores 0
Physical anomalies: deep penetration, jumps in object speed or kinetic energy, objects leaving bounds or falling through the floorStage credit gained within the anomaly window does not count; above a severe threshold the whole run is void
Command-pattern and predicate anomalies: high-frequency jitter, sustained torque saturation, stage values jumping to full in one frame, stage values without contact evidenceStage credit within the window does not count, and the episode is flagged
Fabrication: rollouts whose provenance does not check out; scoring without ever reading sensorsThe first voids the run; the second has its score discarded and is flagged
Never ran, verifier error, a result that is not finite or outside [0, 1]The episode scores 0, with the reason recorded
The 3 grading runs of an episode differ beyond the toleranceScored as the mean of the three, flagged as not reproducible, and passed to the maintainers to fix the task
Reasonable unconventional solutionsCredit for the states reached, no back-filling of skipped stages (section 07 of the task design guide)
Anything uncertainHandled automatically on the side less favourable to the agent, and flagged; never decided by a person case by case

Rules and thresholds are frozen before evaluation. Flagged episodes are collected for the task maintainers: if they reveal a hole in the verifier, a simulator problem or a missed shortcut, the task is fixed and released as a new version, and every agent is re-graded automatically on it; no individual episode's score is edited by hand.

What changes in the verifier and scoring

  • Alarms are output grouped by the three questions, with timestamps and trusted-log excerpts: in evaluation they drive automatic handling and flags; in task checks they let a person jump straight to them.
  • Every kind of alarm has a fixed automatic handling rule (table above), frozen before evaluation; anything uncertain is handled conservatively.
  • Reports give the automatic score and the flagged episodes with reasons; there is no manual re-scoring step.
  • After a revision of the task or its verifier, every agent is re-graded automatically on the new version.

06 · Monitors against reward hacking

Watching online, from the environment side

All monitors run on the environment side; their alarms go to the trusted directory and are read by the verifier. Unambiguous alarms void a run directly; alarms that could come from legitimate control are handled by frozen rules: stage credit within the alarm window does not count, and the episode is flagged (section 05). Thresholds are frozen before evaluation. Every monitor needs two test sets: exploit runs that must trigger it and oracle runs that must not.

MonitorWhat it watches
InterfaceUnknown methods, wrong tokens, malformed frames, reset outside development mode
World integrityScene sealed before the agent connects; masses and friction hash-checked every 500 steps; teleports (>20 m/s)
Physical anomaliesPenetration depth; maximum object speed; kinetic-energy jumps not matched by the robot's work; objects leaving the room or falling through the floor
Command patternsHigh-frequency jitter (the usual way to pump energy into an object), sustained torque saturation, sustained pushing against joint limits
Predicate anomaliesA stage value jumping to full in one frame; stage credit without contact evidence; progress spiking and immediately falling back
Resources and timeWall-clock budget, simulated time, observation count; the container's processes, memory and CPU
NetworkConnection attempts outside the internal network; requests the proxy refused
VideoThe environment's top-down video (onboard camera views later)

07 · Against fabricated outputs and inputs

Trust only what the environment recorded

The principle: what the agent says and what files it writes are not evidence; the only evidence is what the environment side recorded itself. The table covers fabricated outputs and fabricated inputs.

Forged transcript or costRewriting its own transcript, under-reporting token useThe launcher records the agent's stdout outside the container; LLM requests and token counts should be metered independently by a trusted proxy, not taken from the agent's own statistics

08 · Attack categories and defences

Distrust by default: credit only on firm evidence

Corresponds to R7 of the task design guide: designers write their attack list by these categories and deliver negative cases and exploit tests (see section 09 of the task design guide).

Valid success = goal reached ∧ contract satisfied ∧ integrity passed (v5 section 15). Thresholds, windows, tolerances and anomaly handling are frozen before evaluation. Every category below needs a defence in the task design and evidence at acceptance. Grading is automatic; people check only when a task is admitted (section 05 of task acceptance).

Handling suspicious runs

  • Any integrity alarm: the whole run is voided automatically (VOID) and scores 0.
  • Other alarms are handled by the rules of section 05: the affected stage credit does not count, and the episode is flagged.
  • Flagged episodes are collected for the task maintainers; a confirmed hole or missed shortcut joins the negative cases or fixes the predicates or monitors in a new version, and every agent is re-graded automatically.
  • No individual episode is re-scored by hand.
