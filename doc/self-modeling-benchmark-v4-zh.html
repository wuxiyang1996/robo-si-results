01

Terminal-Bench for embodied agents

给 agent 一个目标、一具或多具身体，以及可交互的物理世界。让它写代码、发现工具用途、组合技能并修订 harness，完成长程任务。

第四版以 tool use + coding + harness writing 为主线，暂称 Embodied Terminal-Bench。VLA、全身控制器与原子技能提供执行能力；coding agent 负责观察、物理推理、实验、程序组合与恢复。Humanoid、manipulator、quadruped 与 multi-robot 是目标覆盖范围，首批任务归入工具发现（Tool Discovery），以人形与多机器人作为身体配置标签。其中双 G1 长箱搬运（M2 / Version B）、G1 推车辅助重物运输（H2 / Version C）、G1 自动回弹门穿越（H3 / Version D）与 G1 斜坡/桥梁搭建（H4 / Version E）均为 P0 优先实现任务。利用机器人作为工具的高架取球（M3 / Version F）以 P0/P1 加入创造性工具使用与协作评测。杠杆辅助重物抬升与运输（H5 / Version G）以 P1 加入机械增益与多阶段工具组合评测。双四足运输（M4 / Version H）以 P0 加入 Go1/Go2 协同牵引评测。

核心假设：在相同执行器、观察与资源预算下，能编写和调试程序的 agent，比直接 VLA 或仅调用固定技能的 agent 更擅长多步物理问题；可复用 harness 能把探索成本摊薄到后续任务。两点均需实验验证。

相对 v3：能力发现与 self-modeling 保留为 RQ3 的机制检验；主问题回到 coding agent 是否真正帮助机器人。训练默认关闭，可另设有明确预算的轻训练；可变形物体是扩展项。降低求解延迟是设计目标，不把“现有工作普遍很慢”当作已验证结论。

本文是研究与工程提案。Benchmark 接口、预算、任务和实验均待实现；三套执行器的独立仿真进展见控制器验证状态，不代表任务已经可执行。旧版 benchmark v3 与 V3 方法提案 [external workspace]继续独立保留。

02

三个研究问题与可证伪实验

RQ1 · Coding agent 是否帮助复杂机器人任务？

比较直接 VLA、同一推理模型的固定技能调用、可编程 agent，以及能持久修订 harness 的 agent。匹配底层技能、传感器、任务、token 与交互上限；比较锁定预算下的有效成功率、恢复率和耗时。直接 VLA 是系统对照；“代码是否有用”的因果证据来自同模型、同接口的调用—编程消融。

反证：收益只出现在更强执行器、更多重试或更长预算下；或者技能覆盖匹配后，代码组的成功—成本曲线没有改善。

RQ2 · 如何在 sandbox 中检验物理推理？

把 robot brain 定义为可检验的“假设 → 预测 → 探测 → 更新 → 执行”闭环。比较纯观察、同预算随机探测、有信息量的探测，以及移除反馈后的版本。记录行动前的成功概率和约束预测；用世界物性干预与实际执行评估更新是否有效。

反证：解释文字更完整，但预测校准、探测效率或最终成功没有提升；推理结果仅依赖隐藏状态泄漏。

RQ3 · Self-modeling 是否带来跨身体收益？

固定场景和目标，改变 reach、gripper、力矩或已验证的移动能力。比较无持久记忆、等容量一般经验记忆、显式自身/世界能力记忆，以及完整能力信息的诊断上界。检验迁移后的计划适配、能力校准与样本效率。

反证：等容量一般记忆已解释全部收益，或 self-model 只记住机器人名称；在新身体、无关变化和无需换策略的控制条件下不成立。

03

三条评测 track：求解、复用、轻训练

A / SOLVE

回合内编程求解

固定 VLA/控制器和公共技能。Agent 可写代码、分支、循环、局部记忆与恢复逻辑，但不改模型权重。每个测试实例清空跨任务记忆；episode 内预算允许的重试全部计费。

B / BUILD A HARNESS

开发后冻结复用

在开发任务上构建 perception wrapper、技能组合、参数估计、失败检测与调度代码。提交源码、依赖锁、说明和技能库快照；隐藏测试前冻结，单独报告开发成本和测试成本。

C / LIGHT ADAPTATION

可选的受限学习

仅允许预声明的小型 adapter、校准器或技能微调，公布可训练参数、数据量、更新步数与 GPU 时间。与零更新对照匹配总预算；独立排名，不与 training-free 结果混合。

“Training-free”指本 benchmark 内无权重更新，不表示预训练控制器没有训练成本。持久代码/技能库变化也属于学习，应记录版本。不得把完整任务答案包装成公共原子技能；复合技能只能从允许的开发经历形成。

04

Robot brain、harness 与执行器

慢速推理与快速闭环分离。Agent 在技能边界或失败事件处决策，冻结的控制器维持控制周期。LLM 超时由 executor 进入已验证的保持/停止状态。语言子目标须转成有类型的对象、位姿、接触、时间范围与终止条件；没有可用控制器的技能要标成 coverage gap。

候选公共原子接口为 observe、navigate、reach、grasp、place、push 与经验证的 step。Handoff 由显式双方动作和同步条件组成。必须公布每个 body/controller 支持的接口、单位、坐标系、有效参数和可观察错误，不能通过隐藏调用语法考 agent。

G1 全身控制器：本机安装与初步验证

更新于 2026-10-16。以下是独立 MuJoCo 仿真中的短时运行结果，尚未接入本 benchmark 的任务、RPC 与 verifier。测试环境为 WSL Ubuntu 22.04、Python 3.10、RTX 5090（32 GB）与 PyTorch 2.8.0+cu128；三个项目分别使用独立环境。

GR00T WBC

已验证：Decoupled WBC 的 Balance / Walk ONNX 策略在 MuJoCo 中连续运行 2,000 个物理步（10 秒），切换站立与行走命令后状态及动作数值有限，最终机身高度约 0.743 m。

候选用途：作为 G1 站立与移动执行层，后续验证操作技能与移动的组合。

未验证：SONIC 控制器、VR、实机、训练及各 benchmark 任务中的负载与接触能力。

HANDOFF

已验证：自带 ONNX 策略在同步 MuJoCo 循环中运行 10,000 个物理步（10 秒），状态数值有限，最终机身高度约 0.787 m；修复 ROS 线程退出流程后正常结束。

候选用途：评估任务空间命令到 G1 全身动作的执行接口，逐项校准移动、机身高度和双腕目标。

未验证：上述命令的完整能力范围、训练、VR 与实机；当前默认模型缺少夹爪关节，夹爪控制禁用。此处 HANDOFF 是项目名，不代表双机器人交接技能已经实现。

ULTRA

已验证：自带 teacher checkpoint 成功加载，使用官方数据中的一个 largebox 动作样本完成 MuJoCo 回放并生成视频。

候选用途：提供动作跟踪执行基线，后续评估移动与操作组合的覆盖范围。

未验证：student 策略、自主任务成功率与完整训练；未安装旧版 IsaacGym Preview 4。teacher 回放不等于视觉自主操作已跑通。

接入门槛：三者目前是已安装并完成初步仿真的执行器候选，不计作 H1–H5 / M1–M4 的任务成功证据。下一步先统一坐标系、命令单位、观测边界、超时/停止与重置接口，再逐项测量原子技能成功率、延迟、接触和载荷范围。同一消融内固定控制器、权重与技能覆盖；不同控制器的结果单独报告。

不给工具用途说明；明确观察与接口

区分 API tool calling 与 physical tool use。API 的操作语义公开；场景中哪些物体可当工具、该怎样组合、哪条路线能成功，不向 agent 标注。物体使用中性 ID，不出现 correct_step_box、用途标签或解法图；自然语言任务只陈述目标与公开有效性约束。

Agent 可以看到外观、空间关系和传感器允许的物理反馈，自主估计承重、摩擦、可移动性、可抓取性与支撑关系。发现“可以用作台阶”不同于知道“调用 step 的参数格式”。禁止任务专属的 solve_shelf()，允许可迁移的移动、接触与抓取技能。

视觉

基础 RGB + proprioception；RGB-D 作为明确的传感器变体，记录分辨率、帧率、延迟与标定。不能在视觉 track 中偷偷补充仿真器精确物体位姿。

接触与触觉

力/力矩、接触或 tactile 作为可选扩展，声明可用部位与噪声。传感器缺失与低质量信号分别记录。

文本 grounding

由允许的感知管线产生对象描述，附来源和置信度。使用真实状态生成的文本只进入单列 oracle track；文本不描述推荐用途。

沿用 v3 的 Explicit / Partial / Latent 能力信息设置。它是独立实验轴，与下面的难度等级和传感器组合分别报告。主比较建议 Partial，Latent 用于发现诊断，Explicit 用于信息上界。

06

难度课程：从用途发现到不确定执行

  1. L0
    所有候选物体都有可用功能

    无干扰物，物性可靠；agent 仍需选择、排序并调用技能。“有用途”不表示每件物体都必须用，也不提供用途说明。

  2. L0.5
    用途不直观 / 物性变化

    外观相似但高度、摩擦或承重不同；常见物体可被重新利用。需要从可观察证据或预算内互动判断。

  3. L1
    相关物体与无用物体混合

    增加 distractors；选择不使用某物体也是正确决策。保持有效解路线，避免只增加视觉拥挤。

  4. L1.5
    看似有用的陷阱

    如易滑的支撑、会倒的箱体或导致死路的资源。陷阱要有可获得的证据或探测机会；无法辨别的情况应允许不确定性。

  5. L2
    对抗、故障与不确定性

    加入弱化 gripper、传感器退化、动作噪声或受控扰动。先做单因素实验，再组合；agent 需感知失败、恢复或合理停止。

将笔记中 L1 的附加难度记为 L1.5，避免与 L0.5 重名。等级是课程标签，不是已经测得的难度排序；用失败分布与代价验证。陷阱、物性、故障与观测噪声保留独立标签，失败率不可全归为推理能力。

现有任务分类：9 个任务，4 个目标类别

上位类别统一为工具发现（Tool Discovery），主分类按任务目标划分，便于比较同类问题在不同身体上的表现。物理机制、身体配置与实现状态分别作为独立标签；保留 H1–H5 / M1–M4 编号和现有目录，不因重新分类而改名。

1 · 高处取物与可达性扩展

H1、M1、M3。将不可直接访问的目标取出并交付。机制包括搭建支撑、容器姿态调整、异构机器人分工，以及将另一台机器人举升或支撑为工具。M1 侧重角色分工与交接；M3 侧重发现机器人作为工具的用途。

2 · 重物 / 长物运输

H2、H5、M2、M4。克服负载或几何限制，将物体运到目标区。分别考察推车承载、杠杆机械增益与支撑转移、双 G1 分担负载，以及双四足牵引和张力协调。

3 · 动态障碍处理

H3。运输过程中处理会自动恢复的通路约束。核心机制是保持门开启、验证工具是否有效，以及开门—放置工具—重新抓取—通过的时序组织。

4 · 通路搭建与地形改造

H4。将材料组合成可通行结构，再完成取回或交付。核心机制是坡道 / 桥梁构造、支撑与联合载荷稳定性验证。与 H1 的局部触及高度扩展相比，这类任务要求验证整条通路的可通行性。

07

工具发现 — 人形机器人

主类别：工具发现（Tool Discovery）。身体配置：人形机器人（Humanoid）。推车辅助运输（H2 / Version C）、自动回弹门穿越（H3 / Version D）与斜坡/桥梁搭建（H4 / Version E）均为 P0 优先实现任务。杠杆辅助重物抬升与运输（H5 / Version G）为 P1。H4 另设需独立验证的四足和轮式机器人变体；搭建支撑取物（H1）保留为独立示例任务。Humanoid 与 Multi-Robot 是身体配置标签，不是任务主类别。

Version G — G1 Lever-Assisted Heavy Object Lifting and Transport

H5 · P1 · Tool Discovery · 人形机器人 · 任务定义阶段

单台 Unitree G1 需要将一个超过自身直接举升能力的重箱子移动至指定区域。环境中存在长杆、支点块、垫片、滚筒和其他可交互物体，但没有预先提供工具使用说明。Agent 需要自主探索如何利用这些物体改变受力条件，完成重物的抬升和运输。

  • G1 无法直接抬起重箱子。Agent 需要通过物理交互认识自身的举升能力、抓取限制及箱体的质量分布，判断直接搬运为什么不可行。

先测每台机器人单独求解。构造“必须合作”和“合作仅改善成本”两类；不能因场景里有两台机器人就宣称任务检验了合作。若存在单体有效捷径，应如实计分并修正标签。
物理变化
容器开口、末端执行器尺寸、容器质量和物体形状影响角色分配。方块和球分开变体；球的滚动、抓持及接收区保持需独立验证。
成功合约
正确物体从容器中取出并到达目标区；容器和其他物体满足预声明约束，交接连续且无穿透；双方动作、等待、失败与总机器人工作量完整计费。

同步设计：先实现确定性的顺序调度，之后再允许并行动作。显式记录占用区、handoff-ready、grasp-confirmed 与 release 条件；不把小车当可承重台阶，除非该用途在当前配置中经过物理验证。

09

任务扩展与长程定义

长程由依赖深度、工具组合、持续状态和恢复需求定义，不由视频时长或重复动作数定义。记录关键依赖节点、决策数、仿真时间与实际墙钟时间；部分进度由可验证状态定义，不要求复现一条标准路线。

  • 普通操作：搬运、取放、开合与重定位作为原子技能和端到端控制基线。
  • 推理密集：物理 Hanoi、嵌套容器与阻挡移除，检验先后顺序、暂存与约束遵守；符号解题正确仍需真实抓放执行。
  • 资源构造：箱体阶梯、桥/坡道或长杆改变可达性；要求真实受力、接触和通行能力。
  • 身体覆盖：固定臂先验证桌面工具；人形验证支撑与全身过渡；四足从导航、推物或已支持的机械臂动作开始，不假定每个四足都能抓取。
  • 可变形物体（可选）：布料拉动物体、柔性袋装取物或绳索牵引。需要匹配的仿真与控制器、形变/接触判据和独立吞吐测量；首批不依赖它们。

自动任务生成可提出物体、目标和约束组合，但不能直接扩充正式测试集。每个候选需控制器可行性、稳定性、评分反例、解法去重及数据划分审查；只靠物体 teleport 成功不算机器人可行性证据。

10

跨身体与 self-modeling：固定世界，改变能力

(Goal, World, Resources, Budget) 固定 Body / End-effector / Validated controller capability 干预 历史证据 → 自身与世界信念 → 资源选择与可行策略

能力记忆记录“在什么条件下能做什么”，包含预测、置信度、证据来源和失效条件。例如 reach 必须关联站姿和支撑状态，载荷必须关联抓持、速度与稳定性。一次失败不能自动判为身体极限：物体质量、摩擦、感知和控制器误差都是竞争解释。

  • 干净干预：先只改变 reach、gripper 开口、力矩或移动能力之一；真实修改几何/动力学/控制配置并重新验证，不只改描述字段。自然不同型号作为后续泛化测试。
  • 一箱 / 两箱：同一场景可对比不同有效 reach；更改身体也可能影响平衡和视角，需记录这些伴随变化。方案多解时，不把“换了策略”本身计为正确。
  • 四类对照：必须换路线、仅效率偏好改变、同路线仍有效、资源下无可行解。不可解标签须限定验证范围，不能仅因一个 agent 失败而认定。
  • 泛化划分：按身体家族、物体几何、机制和布局分组留出；机器人改名、颜色变化和隐藏无关变化可检查名称记忆及过度适应。

同时保留 world-only 干预来检验自身/环境归因。完整能力上界与真实状态上界单列，不进入公平主比较。显式 self-model 是待验证方法，不是 benchmark 的参赛要求。

11

分步课程、RSI-WM 扩展与数据飞轮

  1. 建立原子技能基线。使用已有控制器，独立测量移动、抓取、放置、推物和可用踏步技能；失败先归因到执行覆盖。
  2. 学习单个 affordance。在开发场景中尝试支撑、推动、延伸 reach 等机制；写下有条件的技能和失败证据。
  3. 组合前置条件。先搬开阻挡，再取工具；先验证支撑，再攀登；通过新布局检查技能是否可复用。
  4. 冻结后完成最终目标。在未见组合、物性与身体上测试；测试回合允许 track 内的适应，但不能把测试 verifier 结果写回课程。
  5. 下一轮开发。仅用开发/训练池的可信轨迹、失败和代码修订更新技能库；再冻结一个新版本做独立评测。

RSI-WM 扩展在本文中的含义：把“选择实验 → 获取物理证据 → 修订 harness → 改善最终任务”作为拟议课程闭环，不假定已经接入某个外部实现。世界模型可以是结构化信念或有界预测器，不强制训练大型视频世界模型。

数据飞轮要测收益：记录有效轨迹率、有效行为/策略多样性、每条有效轨迹成本，以及相同数据量/训练预算下的下游成功率。对照固定脚本随机化与无课程采样；所有扩增轨迹重新验证。主线先评估代码/技能复用，可选轻训练再检验小规模 VLA 数据收益，不把大量新轨迹等同于能力提升。

12

把快做成评测指标，而不是口号

性能目标：预训练执行器持续控制，agent 用少量关键观察进行规划与程序调试。先测执行器闭环上限、仿真吞吐、模型调用等待、图像处理、初始化/重置成本，再决定可负担的任务规模。

降低重复开销

固定依赖与预热模型；复用进程但彻底重置 episode 状态；在开发阶段缓存通用技能。以动作块和事件触发观察减少 LLM 回合，保留失败与关键接触视频，完整状态日志在可信端留存。

预算公平

统一 wall-clock、LLM tokens、模拟步数、重置次数、GPU 时间与并发数上限。工具探测、失败、内部重试、两台机器人的工作量和代码运行均计费，不能只统计最终成功录像。

建议 pilot 先测 5 / 15 / 30 分钟的 success–budget 曲线；这是待校准的预算网格，不是已实现速度或实时性保证。使用同一轨迹的预算前缀与预定 checkpoint，避免每档重新挑最好的随机种子。Verifier 只离线读取，不向求解 agent 返回分数。

分别报告端到端冷启动时间、预热求解时间、模拟物理时间、总计算成本与摊销成本 (开发成本 + N 次测试成本) / N，注明 N。Track B 不能只报冻结 harness 的快速执行而省略昂贵开发。多机器人并行降低的墙钟时间与增加的总工作量同时报告。

13

Harbor sandbox 与可信物理边界

采用 Harbor 编排任务、agent 和 sandbox；利用其 separate-verifier 机制作为独立评测基础。容器隔离不是杜绝 reward hacking 的保证。以下是本项目拟实施的隔离协议，仍需实际验证。

  1. Agent workspace：只挂载公共指令、SDK、允许的依赖和可写代码目录。私有 TaskSpec、解法、真实物性、隐藏种子和评分脚本不进入该容器。
  2. 可信 simulator worker：在 agent 权限之外维护状态与物理参数，只提供传感器、动作和有预算的开发 reset。禁止任意 Python eval、状态 setter、文件读取和引擎调试接口透传。
  3. 隔离 verifier：只由可信端读取状态日志/轨迹及提交物。评分输出不可写；冻结程序在干净环境与隐藏实例上重放。在线 Track A 使用可信记录的闭环轨迹，复测时重新运行 agent。
  4. 最小可达范围：锁定依赖，任务运行时网络仅允许所需模型代理和执行 RPC；无宿主 Docker socket、无特权模式、无评分目录挂载，检查 IPC、进程与错误日志是否泄漏。
  5. 审计与反例：测试篡改 client、伪造成功日志、越界 RPC、读评分文件、跨 episode 残留等情况；物理异常另由接触/能量/连续性诊断和视频复核发现。

开发阶段可以重置、试验并查看公开的执行反馈；测试阶段只允许该 track 声明的 reset 次数与观察。容器限制只能减少软件篡改和泄漏，不能自动识别仿真接触漏洞；两条边界分别评估。

14

Verifier：成功、工具理解与异常行为

双通道证据：可信仿真合约负责对象身份、目标区域、保持时间、接触、稳定性与约束；同步视频供人类复核策略、异常接触及评分分歧。固定机位与 robot-view 视频保留时间戳。Video judge 不替代状态合约，仿真状态也不能仅凭“看起来合理”证明真实物理正确。

有效新解法

满足公开约束和目标，连续物理执行，能在小扰动和重新运行中复现；用不同工具组合或角色分配完成任务。无需匹配参考路线。

物理 / 合约漏洞

穿透、能量异常、非预期引擎行为，或终态计分成功但实际物体取错。标记为待审查或无效，不计入有效成功或训练正样本。

评测篡改 / 泄漏

修改奖励文件、读取隐藏答案或调用状态 setter。根据访问和动作证据标记违规，不凭 agent 的解释猜测其意图。

工具理解不由最终成功反推。在诊断回合记录用途/属性预测，再移除工具、交换物性或改变身体，观察计划和执行是否相应改变。语言解释只作辅助证据；诊断询问的额外 token 与延迟单列，不污染主速度比较。

  • 主要结果：有效成功率随预算变化；同种子配对成功差与置信区间。成本报告 tokens、墙钟、GPU/机器人工作量和每个有效成功的成本。
  • 推理与适应：失败后的恢复率、有效探测代价、能力预测 Brier score / 校准、约束归因、必须换路线与应保持路线的分别准确率。
  • 行为审计：新颖有效策略比例、漏洞/篡改率、未决案例比例；公布分母。由两位不知道方法身份的评审独立标注异常/新颖性，分歧进入复核。
  • 基础设施结果：崩溃、超时、执行器缺失与 agent 失败分开。运行总数和基础设施失败必须披露，不能静默删除不利样本。

主指标可写为 ValidSuccess = GoalReached ∧ ContractSatisfied ∧ IntegrityPassed。阈值、窗口、容差和异常处理在评测前固定；结果未决时分别给出保守统计与未决数量。参考解仅证明可行性，不定义唯一合格路线。

15

最小实验：先验证 coding 收益，再扩展

起点：优先完成 H2、H3、H4、M2 与 M4 的执行器门槛，再完成 H1 与 M1，为每族创建直接/简单、工具必需、受扰动三个经过验证的条件。每个条件用分离的开发、验证和隐藏测试场景；同源布局、变体和轨迹不能跨 split。首轮小样本用于发现失效与估计方差，正式 seed 数按方差和可负担预算预注册。

  1. B0 / Direct VLA：同一冻结 VLA，目标输入与正常反馈，作为端到端系统基线；不支持的身体单列，不用不同控制器冒充同条件。
  2. B1 / Fixed-skill agent：同一推理模型、同一感知和技能，仅逐步调用，无任意程序和持久 harness 修订。
  3. B2 / Coding agent：相同接口下允许代码、循环、分支与反馈调试；Track A 衡量回合内收益。
  4. B3 / Reusable harness：基于 B2，允许开发阶段跨任务技能积累，随后冻结；Track B 报告开发和摊销收益。
  5. 诊断参考：手写可执行脚本测 executor coverage；完整能力信息测信息上界。二者不混入 agent 排名。

RQ2 在 B2 上做 observation-only / random-probe / informative-probe / removed-feedback 消融；RQ3 比较无记忆、一般记忆与 self-model，限制同样的存储、token 和试验预算。轻训练、传感器与多机器人调度变化在主效应成立后逐项加入。

统计单位：重复相同任务的独立求解种子，按任务/场景簇计算配对不确定性，不把视频帧当样本；同时报告每族结果，避免长任务权重过高。隐藏测试只用于最终比较；若据此改方法，启用新的测试留出集。

决策规则：若脚本无法稳定执行，先修执行器；若 coding 没有改善匹配预算下的有效成功，先分析失败与代价，不靠增加任务数量支撑主张；若收益只来自已见路线，增加机制/身体留出而不是扩大同分布变体。

相关工作：承认重叠，定位待验证贡献

以下基于官方论文/项目资料，核查日期 2026-10-10。每项“本项目比较”是研究设计判断，不能据此断言已有工作缺少某种能力。

  1. Terminal-Bench借鉴终端中目标驱动的 agent 评测形式。官方项目。本项目比较：程序提交的价值最终由物理执行而非文本答案决定，另计身体与控制器限制。
  2. EmbodiedSWE / EmbodiedSWE-Bench · 主要参考已覆盖长程机器人 coding-agent 求解、跨身体迁移、解法数据扩增与任务生成。官方项目。本项目比较：重点验证预算受限的技能 harness、未标注用途的工具组合与能力干预；长程、自动生成和数据飞轮本身不构成区别。
  3. RLE-Bench九个任务族覆盖交互控制、策略学习、感知估计与机械设计；其中已有 reusable harness 任务。技术报告 · 代码。本项目比较：限定零/轻训练、对齐执行器，并检查工具发现、身体干预和成本曲线。不能只凭“写 harness”主张新颖性。
  4. RoboTool以语言模型生成控制代码来处理隐式物理约束与创造性工具使用。论文。本项目比较：系统化用途隐藏、干扰/陷阱、物性变化与跨身体配对。
  5. RoboWits针对机器人创造性问题求解、工具使用与意外条件的双臂 benchmark。官方代码。本项目比较：把故障和不确定性纳入 L2，并单独测试 coding 与可复用 harness 的作用。
  6. ENPIRE以 reset、rollout、verification 与 policy improvement 构成现实机器人迭代闭环。官方项目。本项目比较：借鉴可重复反馈，主线聚焦冻结执行器与受限开发成本，不依赖大规模策略训练。
  7. ASPIRE从执行轨迹诊断与修复控制程序，并积累可复用技能库。官方项目。本项目比较：检验课程与技能记忆在未见身体/物性上的收益，并完整计入开发与推理成本。

拟议贡献组合：匹配执行器下的 coding 效果；不提示用途的物理工具发现；受控身体与世界变化中的自我建模；可审计的有效解法/漏洞区分；预算明确的课程与复用。每项都需要实证，不作“首次”主张。

实施顺序与第四版交付边界

  1. G0 · 复现与选型。先复现一个 EmbodiedSWE 刚体任务及评分，再复现一个可用的 VLA/原子技能接口。保留 v3 的复用优先思路，锁定上游版本；控制器选择以支持身体、技能成功率和延迟为依据。
  2. G1 · 可信桥接。打通 Harbor agent container → RPC → simulator → verifier，验证观察边界、预算计量、重置和篡改反例。输出运行清单、威胁模型与失败记录。
  3. G2 · 可执行 seed。优先完成 H2、H3、H4、M2 与 M4（P0），按 P0/P1 纳入 M3 并独立验证举升/支撑与精确抓取能力，同时完成 H1/M1；H5 按 P1 纳入，先验证杠杆接触控制、支撑转移与完整运输；每个任务均需脚本、视频、success predicates、物理有效性和负例。踏箱等缺失能力作为明确 blocker，不用隐藏宏替 agent 解题。
  4. G3 · 最小对照。运行 B0–B3，给出预算曲线、失败归因和 executor coverage；先回答 RQ1，再做 RQ2/RQ3。
  5. G4 · 课程与泛化。加入 L0–L2、身体/末端执行器变化、冻结技能库与机制留出；检验数据收益。更多身体、可变形物体与第二仿真器随后按覆盖逐项加入。

任务包草案：公开目标与限制、环境/依赖清单、body/controller manifest、传感器与 disclosure 配置、预算与 split ID；私有生成种子、成功合约、能力标签与负例；输出程序、harness 快照、计费日志、可信轨迹、视频和审计结果。这里是自定义 robotics 合约，不声称这些字段已经是 Harbor 原生格式。

首个可发布结果：两类真实可执行任务 + 一套可隔离/计费的 harness + 对齐基线 + 有效成功/耗时/漏洞审计。任务数量和实现速度由可行性与试跑决定，不用大规模训练填补未验证的技能。

第四版交付包括中英双语研究网页与版本导航；2026-10-16 补充了 GR00T WBC、HANDOFF 与 ULTRA 的本机安装和独立 MuJoCo 初步验证记录。尚未训练模型或运行本 benchmark；任务接入、技能覆盖与正式实验仍待完成。公开材料需区分设计目标、实现覆盖与测得结果。

最新实测：物理约束 fallback 在当前场景登箱成功

2026-10-16，G1 在现有 Genesis 柜子场景从箱前地面站姿登上 18 cm、5 kg 的可动箱子，45.885 秒时达到连续 2 秒双脚稳定支撑。采用显式全身 IK、接触力规划和状态反馈 WBC；开启自碰撞，执行中不写根节点位置、不托举、不绑定箱子。箱子水平位移约 0.856 mm。此结果不属于 N1.7 + SONIC。

参考轨迹限速 1 rad/s、离散加速度限制 4 rad/s²；实际最大控制力矩约为模型上限的 44.51%，最大关节速度为对应上限的 2.94%。独立加密碰撞检查通过。仅验证一个初态，从远处走近及搬箱后接续登箱尚未验证。

Arena 搬箱 checkpoint 已接入当前场景，但最新测试在 17.72 秒跌倒，录像显示推碰/翻动箱子，没有完成抓取搬运。原 Arena demo 的搬运成功不能移算到当前场景。
