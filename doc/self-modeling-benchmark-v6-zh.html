02 · 问题与范围

把 Terminal-Bench 搬进物理世界

VLA、全身控制器和原子技能提供执行能力；coding agent 负责观察、物理推理、做实验、组合程序和从失败中恢复。目标覆盖人形、机械臂、四足和多机器人；首批任务以人形和多机器人为主。

核心假设：在相同的执行器、观察和预算下，能写和调试程序的 agent 比直接 VLA 或只调用固定技能的 agent 更擅长多步物理问题；可复用的 harness 能把探索成本摊到后续任务上。两点都要实验验证。

本页和其他各页的分工

  • 本页：研究问题、评测 track、实验设计、任务分类与进度、路线图。
  • 规范：任务怎么设计、怎么验收、沙箱怎么隔离、怎么评分、评测怎么组织，各在一页：任务设计、任务验收、隔离沙箱、评分与验证、评测规程。
  • 进度细节：在实现状态页。
  • 边界：这是研究与工程提案。还没有跑过 LLM agent，也没有正式实验结果。

03 · 三个研究问题

三个研究问题，各自怎么证伪

问题怎么比什么结果算否定
RQ1 · coding agent 是否帮助复杂机器人任务？直接 VLA、同一推理模型的固定技能调用、可编程 agent、能持久修订 harness 的 agent；匹配执行器、传感器、任务和预算，比较有效成功率、恢复率和耗时收益只出现在更强的执行器、更多重试或更长的预算下；技能覆盖匹配后，代码组的成功—成本曲线没有改善
RQ2 · 怎么在沙箱里检验物理推理？把决策写成“假设 → 预测 → 探测 → 更新 → 执行”的闭环；比较纯观察、同预算随机探测、有信息量的探测和移除反馈；行动前记录成功概率和约束预测解释更完整，但预测校准、探测效率或最终成功没有提升；推理结果依赖隐藏状态泄漏
RQ3 · self-modeling 是否带来跨身体收益？固定世界，改变 reach、夹爪、力矩或移动能力；比较无记忆、等容量一般记忆、显式能力记忆和完整能力信息上界；第 2 层难度在场景里考同一件事等容量一般记忆解释了全部收益；self-model 只记住了机器人名称

直接 VLA 是系统对照；“代码是否有用”的因果证据来自同模型、同接口的调用—编程消融。

04 · 评测 track

三条 track：求解、复用、轻训练

track允许什么怎么评
A · 回合内求解固定执行器和任务提供的工具；agent 写代码、做实验，不改权重；每个测试实例清空跨任务记忆主 track。开发会话结束后，交付程序在新的密封回合上重跑评分，见评测规程第 02 节
B · 构建 harness 后冻结复用在开发任务上积累感知封装、技能、参数估计和调度代码；技能只用指定来源，优先 agent 自己产生的 rollout隐藏测试前冻结；开发成本和测试成本分开报告，摊销成本 =（开发成本 + N 次测试成本）/ N，注明 N
C · 轻训练预先声明的小型 adapter、校准器或技能微调；公布可训练参数、数据量、更新步数和 GPU 时间和零更新对照匹配总预算；单独排名，不和零训练结果混排

“零训练”指在本 benchmark 内不更新权重，不表示预训练控制器没有训练成本。持久的代码和技能库变化也算学习，要记版本。不能把完整解法包装成公共技能。

05 · agent、harness 与执行器

agent 只看传感器、只发关节指令

结构和 v5 一致：agent → 可编辑的 harness → 冻结的执行器 → 可信仿真 → 评分器。v6 把它落成了 H1 的隔离沙箱。

  • 隔离：agent 在 Linux 容器里（uid 1000、只读根文件系统、--cap-drop ALL、内部网络），只能通过带令牌的 RPC 和环境一侧通信。8 个方法：info、status、observe、command、command_sequence、declare_infeasible、finish，以及只在开发模式开放的 reset。
  • 传感器：只有机载的相机（RGB 和深度）、LiDAR、IMU 和关节读数。Genesis 1.4.3 没有射线传感器，LiDAR 用四个深度相机拼出来。不给坐标、物体位姿、物性、分割图或用途。
  • 工具：L1 是 GR00T WBC 的站立和行走；L2 是目标点轨迹规划；L3 是中间点加 IK/FK 求解；任务提供时还有 VLA。输入只能是 agent 自己的传感器结果，agent 也可以全部自己写。
  • 技能：技能接口可选。只能用任务指定的技能，以及 agent 自己在开发会话里产生的技能和 rollout；环境一侧按观测摘要核对来源。

详见隔离沙箱第 03 节；agent 能拿到哪些反馈见隔离沙箱第 05 节。

06 · 执行回退与技能沉淀

技能不够时逐级求解，再把成功的程序沉淀成技能

层级做什么失败时
L1 · 调用已有技能从冻结的技能库选已验证的技能，检查前置条件、目标范围和终止条件在剩余预算内升到 L2
L2 · 直接求解轨迹输入当前状态、目标位姿和自己估计的障碍几何，由求解器搜索轨迹返回可观察的诊断，转 L3
L3 · 编写中间状态agent 给出中间点、接触阶段和约束，逐段 IK/FK 求解再拼接修改中间点或约束；预算用完就停

这里的 L1–L3 是执行回退的层级，和难度的三层是两条独立的轴。

沉淀闭环

  1. 保存。成功执行后保存求解代码、参数、状态、动作、接触事件和结果。原任务成功只是候选技能的起点。
  2. 参数化。优先提取求解程序，例如 lift_box(box_pose, box_size, lift_height)，按新参数重新生成运动；只有轨迹时，按接触事件分段成模板。
  3. 验证。在留出的初始状态、目标位置、箱体尺寸和物性变化上重放，并加扰动。
  4. 注册。通过验证才按版本登记，写明适用身体、参数范围、前置和终止条件；之后由 L1 直接复用。

怎么证明是技能，而不是缓存的轨迹

  • 比较固定 L1、L1+L2、L1+L2+L3，以及开、关技能沉淀；加原始轨迹缓存作对照，固定控制器、观测和总预算。
  • 报告候选技能通过率、未见参数上的成功率、后续复用次数、回退频率和摊销耗时。
  • 评分回合的初始状态是随机的，单纯回放 rollout 拿不到分。

进度：L2/L3 在 MuJoCo 运动学副本上已实现，还没接到物理执行，也还没有技能注册。下一步是 Genesis 原生 planner 或 cuRobo 后端、带姿态和接触约束的求解，以及轨迹跟踪执行器。

07 · 观察与工具用途

不告诉用途，只给机载传感器

区分 API 调用和物理工具使用。接口的语义公开；场景里哪些物体能当工具、怎么组合、哪条路线能成，都不告诉 agent。物体用中性 ID，指令只写目标和公开的合规约束，见任务设计第 02 节。

  • 传感器只用机器人原生或可加装的，型号、安装位姿和噪声写进任务卡，见任务设计第 08 节。
  • 接触、力/力矩或触觉是可选扩展，要声明部位和噪声。
  • 用真值生成的文字描述只能进单列的诊断条件，不进主比较。

能力信息轴

沿用 v3 和 v5 的 Explicit / Partial / Latent 三种能力信息设置。它是独立的实验轴，和难度三层、传感器组合分开报告：主比较用 Partial，Latent 用于发现诊断，Explicit 给出信息上界。H1 的 Harbor CPU 版已经按这三档实现（Harbor 版说明）。

08 · 难度与随机化

只分三层，逐层叠加

层场景里有什么考什么对应 v5
第 1 层只有必要的工具和物体发现用途、安排顺序、执行L0
第 2 层再加入这台机器人用不了、换个身体就能用的工具或物体自我建模：知道自己能做什么、不能做什么新增，对应 RQ3
第 3 层再加入干扰项：超出能力范围的、实际不可用的、看着有用但会失败的做实验、排除选项L0.5、L1、L1.5

v5 的 L2（夹爪弱化、传感器退化、动作噪声）不再单独成层：噪声和物性变化并入初始状态随机化，故障作为单独标注的鲁棒性变体。

  • 随机化：能随机的都随机，但不能破坏可解性、不能打开捷径、不能让解题关键只能靠真值得知，见任务设计第 04 节。
  • 子任务：用状态定义完成条件，有能单独开始的起始状态，供课程学习和诊断；子任务场景不给被评测的 agent，见任务设计第 06 节。
  • 难度目标：强 coding agent 要 4 小时以上的迭代。难度试跑时如果第 3 层 4 小时内就被解出，就加深依赖、扩大随机范围或换更难分辨的干扰项。

10 · 跨身体与 self-modeling

固定世界，改变能力

目标、世界、资源和预算固定，只干预身体、末端执行器或已验证的控制器能力。看 agent 能否从证据形成对自身和世界的判断，再据此选资源、选策略。

  • 能力记忆记录“在什么条件下能做什么”，包括预测、置信度、证据来源和失效条件。一次失败不能直接判为身体极限：质量、摩擦、感知和控制误差都是竞争的解释。
  • 干净干预：一次只改 reach、夹爪开口、力矩或移动能力之一，真实修改几何、动力学或控制配置并重新验证，不只改描述字段。
  • 四类对照：必须换路线、只改变效率偏好、同一路线仍然有效、没有可行解（应声明不可行）。
  • 第 2 层难度是同一思路的场景版：身体不变，场景里放入换个身体才能用的工具，考 agent 是否知道自己用不了。
  • 泛化按身体家族、物体几何、机制和布局分组留出；同时保留只改世界的干预，检验 agent 把失败归因给自身还是环境。

11 · 评分与验证

分数只来自环境一侧的记录

  • 评分器在环境一侧，读可信的状态日志，不读 agent 的自述；agent 拿不到分数，见评分与验证第 02 节。
  • 阶段判据要有接触证据、物体身份、保持时长和静止条件；按阶段给过程分，回合取峰值，成功 0/1 单独报告，见评分与验证第 03 节和评分与验证第 04 节。
  • 成功仍定义为 ValidSuccess = 达到目标 ∧ 满足合约 ∧ 完整性通过；完整性报警直接判 VOID。
  • 监视器规则事先冻结，评测全自动；人工只在任务验收时看录像，检查任务和评分器本身，见任务验收第 05 节。
  • 工具理解不从最终成功反推：在诊断回合记录用途和属性预测，再移走工具、交换物性或改变身体，看计划和执行是否跟着变。诊断只用于研究分析，不进主分。

12 · 预算、成本与速度

预算按仿真步数和 token 计，耗时只报告

  • 主预算：仿真步数由环境一侧计数，token 由可信代理计量；观测次数和 reset 次数另有上限；墙钟只用来防卡死，见评测规程第 01 节。
  • 预算曲线：按预算点给交付快照评分，画成功—预算曲线；不在每个预算档重新挑最好的种子，见评测规程第 02 节。
  • 速度：作为次要指标报告冷启动时间、预热后求解时间、仿真时间和总计算成本；Track B 报摊销成本并注明 N；多机器人并行省下的墙钟和增加的总工作量一起报。
  • 先测底座：先测执行器闭环上限、仿真吞吐、模型调用等待和重置成本，再决定可负担的任务规模。H1 在 GPU 被占用时每个控制步约 0.67 s，这也是墙钟不适合做主预算的原因。

13 · 实验与基线

先验证 coding 的收益，再扩展

条件是什么回答什么
B0 · Direct VLA同一冻结 VLA，输入目标，正常反馈端到端系统对照；不支持的身体单列
B1 · 固定技能 agent同一推理模型、感知和技能，只逐步调用，不写任意程序RQ1 的消融对照
B2 · coding agent相同接口，允许代码、循环、分支和调试Track A 的回合内收益

参考专家解读真值的专家解上锚点；证明可解、验证评分器
简单脚本（可选）只用任务提供的技能、不做感知的固定脚本任务是不是靠固定套路就能拿分

标准 agent 配置（版本固定的 coding agent 加默认提示词）就是 B2 的一个实例，也是贡献流程里难度试跑用的配置，见评测规程第 05 节。

  • 重复：每个 agent × 任务独立评测 3 次；每份交付在同一批密封回合上评分 3 次取平均；按任务和场景簇给配对的 bootstrap 置信区间，见评测规程第 04 节。
  • 消融：RQ2 在 B2 上做纯观察、随机探测、有信息量的探测和移除反馈；RQ3 比较无记忆、一般记忆和 self-model，限制同样的存储、token 和试验预算。
  • 决策规则：脚本都不能稳定执行，先修执行器；coding 在匹配预算下没有改善有效成功，先分析失败和代价，不靠增加任务数量撑主张；收益只来自见过的路线，就加机制和身体的留出，而不是扩大同分布变体。

14 · 课程与扩展

子任务支撑课程，新任务必须过验收

  • 课程：原子技能基线 → 单个用途（支撑、推、延伸 reach）→ 组合前置条件 → 冻结后完成最终目标 → 下一轮开发。子任务的起始场景让每一步都能单独练、单独测。
  • RSI-WM：把“选实验 → 拿物理证据 → 修订 harness → 改善最终任务”作为课程闭环；世界模型可以是结构化信念或有界预测器，不强制训练视频世界模型。
  • 数据飞轮：要测收益，包括有效轨迹率、行为多样性、每条有效轨迹的成本，以及同等数据量下的下游成功率；扩增的轨迹全部重新验证。
  • 自动生成任务：可以提候选，但必须走完任务验收才能入库。
  • 扩展项：可变形物体（布、袋、绳）需要匹配的仿真、控制器和判据，首批不依赖。

16 · 路线图与交付边界

做到哪了，下一步做什么

  1. G0 · 复现与选型。三套 WBC、SONIC 和 N1.7 在本机仿真里跑通短测；L2/L3 求解器已实现。未完成：搬箱级的操作能力还只有官方示例。
  2. G1 · 可信桥接。H1 的隔离沙箱已实现：逃逸探针、传感器几何、检查点恢复和评分模式都用脚本 agent 验证过。未完成：还没有跑过 LLM agent；评分和监视的待办见实现状态页。
  3. G2 · 可执行任务。H1 优先：direct 类专家解 10/10，借助凳子的链路跑通 3 次；M2 轻量配置跑通。下一步：H1 按三层重组场景、解决搬凳子、走完验收；其余任务先做参考专家解。
  4. G3 · 最小对照。跑 B0–B3 和基线，给出预算曲线、失败归因和执行器覆盖；先回答 RQ1，再做 RQ2 和 RQ3。
  5. G4 · 课程与泛化。加入身体和末端执行器的变化、冻结的技能库和机制留出，检验数据收益；更多身体、可变形物体随后逐项加入。

v6 交付的是这份中英文提案和各页的规范。还没有训练模型，也没有运行本 benchmark 的正式实验；公开材料要区分设计目标、实现覆盖和测得结果。
