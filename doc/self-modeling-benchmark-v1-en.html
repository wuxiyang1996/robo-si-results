01

From executing a behavior to discovering a solution

The proposed benchmark measures solution discovery: can an agent autonomously find and execute a solution to a complex physical objective when it receives a goal and an interactive environment, but no decomposition or prescribed tool choice?

  1. ExploreObserve the environment and locate uncertainty.
  2. DiscoverFind resources and infer possible affordances.
  3. Probe and planTest capability hypotheses; acquire prerequisites.
  4. Transform the worldMove, support, connect, or repurpose objects.
  5. Replan and recoverUse execution evidence to revise the strategy.
  6. Achieve and verifyReach the requested physical outcome.

Design target: goal-only specification, an explorable environment, resource discovery, latent affordances, long dependency chains, environment restructuring, multiple valid solutions, failure recovery, and a hidden outcome verifier in the same task.

“Open-ended” describes the space of possible solutions within a bounded environment, public interaction rules, and a finite budget. The proposed combination is a research hypothesis to validate against existing benchmarks, not an established priority claim.

02

Self-modeling connects the world to the agent's own limits

World and affordance model

Where are resources? Is this crate movable? Can this surface support a load? These describe the environment and possible interactions.

Capability self-model

Can this robot and executor reach, lift, stabilize, or manipulate this object in the current context? What evidence supports that prediction? These describe the agent–world interaction.

Mₜ = capability hypotheses + execution evidence + uncertainty + invocation context goal → capability gap → diagnostic interaction → update Mₜ → revise plan/harness → act

A useful self-model changes a decision: whether to attempt a grasp, inspect a support, acquire a tool, or abandon a failing strategy. Fluent self-description alone is not evidence. Keep episodic world memory distinct from capability memory, and distinguish a blocked environment from an executor that cannot perform the required action.

Relationship to V3: V3 [external workspace] proposes a method that updates capability memory and a harness around a frozen policy. This page specifies an evaluation setting for that method and other physical agents. Benchmark participation does not require an explicit self-model; its benefit is an empirical question.

The primary test permits within-episode inference and memory updates. Persistent harness learning takes place on development data in a separately declared V3-style adaptation protocol; the resulting system is frozen before held-out evaluation.

03

A physical analogue of terminal problem solving

Terminal setting

A machine, available tools, and an objective. The agent discovers resources, plans, executes, debugs, and checks its work. Terminal-Bench packages tasks with environments and outcome tests. Official introduction.

Proposed physical setting

A robot, a scene, interactable objects, and an objective. The agent explores, infers affordances, acquires resources, restructures the world, executes, and recovers.

The analogy concerns autonomous problem solving and outcome-based evaluation. Physical actions additionally have embodiment limits, contact uncertainty, persistent consequences, and costly resets. A simulator is not an unlimited sandbox that the agent may freely rewind.

04

A box becomes useful because the agent discovers its role

Goal: retrieve the object from the top shelf.

  • robot
  • target and shelf
  • two crates
  • table
  • cart
  • plank
  • distractors

The goal does not name a tool. The following is an illustrative solution hypothesis for an embodiment that supports climbing or elevation; each physical prerequisite must be established.

  1. Discover a reachability gap.Direct retrieval exceeds the robot's current reach.
  2. Explore candidate resources.A crate may be movable and may support the robot; appearance alone does not establish load-bearing ability.
  3. Test a relevant hypothesis.Use a budgeted interaction to assess movability or support, subject to public constraints.
  4. Change the configuration.Position and stabilize a support; climb or reposition only if the embodiment and interface allow it.
  5. Retrieve and check.Complete the goal and inspect observable evidence of success.
Counterfactual: one crate is too low

The agent may investigate a second support or another retrieval strategy. Stacking is only a candidate: height, stability, load, and the robot's ability to assemble it must all be checked.

Counterfactual: the expected crate is absent or weak

The agent must discover a feasible substitute or an alternative mechanism. A toolbox is not automatically a valid support. Task authors must verify that the altered instance still has a permitted solution.

Illustrative task design, not a simulated rollout or demonstrated robot capability.

05

A composite task links discovery to nested prerequisites

Goal: restore power to the workbench.

A two-room scene contains a blocked doorway, cabinet, cart, cable, extension cable, boxes, toolbox, switch, plank, and distractors. Cable connectivity and power are simulator-defined task states.

  1. Inspect the workbench.Determine that power is absent and investigate the cause.
  2. Locate a cable and discover an obstacle.Access is blocked by a cabinet.
  3. Acquire a prerequisite.Unload or reposition the cart, then establish a feasible way to clear the obstacle.
  4. Retrieve the cable and discover a length constraint.Explore for an extension or another valid connection route.
  5. Open access to the second room.Clear its entrance and acquire the needed resource.
  6. Resolve access to the switch.Reconfigure a support or find a different valid activation strategy.
  7. Connect, activate, and verify the outcome.The final state must satisfy the workbench's power condition.

This is one possible dependency chain, not a reference plan exposed to the agent. The final verifier accepts any permitted solution. A family should combine discovery, resource acquisition, physical reasoning, restructuring, and recovery; repeating one known trick many times is insufficient.

The example depends on feasible locomotion, manipulation, support, and connectivity mechanics. Start with a supported subset or another composite goal if the selected simulator cannot implement these faithfully.

06

The task contract makes information boundaries explicit

Task τ = (E, S₀, G, A, V) Protocol P = (O, C, B, reset policy, adaptation policy)
E
Embodiment and declared execution/control interface.
S₀
Initial physical world, including latent properties; the agent receives observations, not the complete state.
G
High-level natural-language goal with a well-defined outcome.
A
Generic parameterized interactions or the declared low-level action interface.
V
Evaluator-owned hidden verifier; its implementation and private predicates are inaccessible to the agent.
O, C, B
Allowed observations, public validity constraints, and interaction/compute budgets.

Agent receives

Goal, embodiment/interface documentation, sensor observations, budget, and public constraints. Generic API contracts specify arguments and failure semantics.

Evaluator retains

Reference plans, gold subgoals, relevant-object lists, affordance labels, successful task trajectories, hidden properties, milestone graphs, and verifier source.

Expose interactions without naming a solution

observe · navigate · grasp · release · push · pull · lift · rotate · place

Arguments refer to observed locations or objects under the declared perception protocol. APIs such as use_box_as_step(), build_bridge(), or retrieve_with_hook() would reveal the intended strategy. Even generic skills must execute through physics, report failures, and avoid exposing oracle feasibility or hidden world state.

The agent can inspect physical consequences and run checks based on its own observations. It cannot query hidden V during a test episode. Resets, if allowed in a separate adaptation setting, consume a declared budget and access only permitted state distributions.

07

Two tracks separate interfaces and expose failure sources

TRACK A / PHYSICAL AGENT & PLANNING

Reasoning agent → generic skills → physics

Use relatively reliable parameterized skills to study exploration, memory, resource discovery, planning, and recovery. Reliability is measured on development tasks, not assumed perfect.

Specify the observation channel; any structured perception variant must be separately reported. Skills cannot teleport objects or provide solution-specific options.

TRACK B / END-TO-END VLA

RGB + proprioception → system → continuous actions

Evaluate the perception-to-action system on the same goal semantics where embodiments and controls are compatible. A reasoning harness around a frozen VLA is one eligible system.

Declare camera inputs, proprioception, action rate/chunks, model weights, and any training or development adaptation.

Scientific question: when does the agent fail to discover a feasible strategy, and when does it fail to execute one? An A–B score gap alone does not answer this: observation quality, interfaces, and skill reliability also differ. Use paired instances, controlled oracle-plan diagnostics, and execution traces to attribute failures.

Report the tracks separately. Align physical-time and interaction budgets where possible; a skill call and a continuous action step are not interchangeable units.

08

Organize tasks by problem-solving structure

  • Reachability transformationChange the configuration to access a target.
  • Tool substitutionFind a functional substitute from observed properties.
  • Tool constructionCompose objects into a useful instrument.
  • Path constructionCreate access across a gap or obstruction.
  • Support and stabilizationEstablish a configuration that stays usable under load.
  • Force transformationUse geometry to redirect or amplify force.
  • Indirect manipulationAffect a target through an intermediate object.
  • Environment restructuringRearrange the scene to enable later actions.
  • Resource acquisitionFind and obtain items needed elsewhere.
  • Nested prerequisitesSolve one access or resource problem to unlock another.
  • Recovery and alternate solutionsRevise a strategy after a consequential failure.
  • Cooperation or instrumental assistanceCoordinate with another agent in an optional later extension.

Annotate each final task with multiple structures, a prerequisite graph, information requirements, and verified solution alternatives. Atom-level tasks can support diagnostics and development; composite objectives form the main test set.

09

Generalization should change causal composition

Seen affordances, unseen compositions

Development includes boxes as supports, planks as bridges, and sticks for retrieval. Test combines them: retrieve a plank → stabilize it → bridge a gap → access a support → retrieve the target.

Unseen affordance transfer

Support experience with crates transfers to a physically suitable toolbox, chair, or other object. Suitability depends on the task and robot, not the category name.

Counterfactual solutions

Remove a familiar tool or change a consequential property while retaining at least one feasible alternative. Test whether the agent revises the solution.

Split by task family, dependency-graph template, object role, and consequential physical property before generating scene variants. Random seeds and textures alone do not establish structural generalization. Include cosmetic changes as controls.

“Seen” refers to the declared development/training distribution; it does not establish what a foundation model encountered in pretraining. Keep test solution templates, hidden predicates, and adaptation feedback isolated. Freeze training data and model/harness versions before evaluation.

10

Score the physical outcome; use progress to explain failure

Primary: final success

Success = 1[goal predicates hold at termination ∧ public validity constraints satisfied]

Examples include target_in_goal_region, power_on, or door_accessible. Define tolerances and any stability interval in advance. The verifier checks simulator state; trajectory similarity to a reference solution is not a success criterion.

Secondary: hidden progress

Progress = satisfied hidden outcome predicates / total hidden outcome predicates

This simple fraction applies when predicates are route-neutral. A hidden milestone graph may explain resource acquisition and prerequisite completion, but must not force the author's preferred route. For route-specific milestones, use prevalidated alternative branches or report them only as diagnostics; a valid final solution receives full success regardless of its path.

Specify whether each check concerns terminal state, an irreversible event, or a sustained condition. Temporary progress must not be counted as intact after a regression. Inspired by LHTB's hidden graded evaluation, use verifiable state/evidence rather than an agent's claimed completion.

Efficiency and recovery

Report action steps, skill/VLA calls, physical simulation time, resets, tokens, wall time, and constraint events. On paired recoverable perturbations, measure final recovery success and its added cost.

Self-model diagnostics

Evaluate capability predictions on controlled probes, using Brier scores/calibration only when probabilities are supplied. Trace a prediction to the probe and plan change it caused. Keep these diagnostics separate from the main score.

Aggregate per task family and split, with repeated instances/seeds, sample counts, and uncertainty intervals. Freeze scoring rules before testing. Public training instances may provide rewards for RL/RFT; hidden test predicates and progress scores remain unavailable as online feedback.

11

Target the joint demands of discovery and composition

EBench

Diagnoses mobile manipulation across skills, horizon, precision, mobility, and controlled generalization axes. It informs capability profiling. Our proposed emphasis is discovering resources and composing a solution. EBench is distinct from EmbodiedBench. Source.

RoboMemArena

Studies memory-dependent manipulation with sequence, counting, occlusion, and transfer tasks. It informs episodic-memory controls; our task contract additionally requires discovering which prerequisites and resources are relevant. Source.

KinDER

Isolates kinematic and dynamic reasoning challenges from perception and language complexity. It is a reference for physical reasoning components and reliable interfaces; the proposed test composes such demands into larger objectives. Paper.

RoboWits

A close neighbor for creative tool use, reasoning, and strategy adaptation under changed conditions. The proposed distinction must be demonstrated through resource discovery, environment scale, and nested composition—not asserted from the name of a task. Source.

PARTNR, BEHAVIOR-1K, EmbodiedBench, HumanoidToolBench, and RoboToolBench also constrain the novelty claim. Compare their information access, action interfaces, dependency depth, resource discovery, alternate routes, and verification protocols. See the V3 benchmark inventory [external workspace] and tool-use methods [external workspace] for RoboTool, iTUP, counterfactual reasoning, and VLMgineer.

The claim to test is the value of the combined evaluation protocol. Physical problem solving, tool use, memory, and long-horizon execution already have substantial prior work.

12

Make solution discovery and self-modeling falsifiable

  1. Direct agent: the same reasoning backbone and executor, with a fixed prompting/interface setup.
  2. Reflection and retry: ordinary execution memory with matched context and reasoning budgets.
  3. Capability-aware planning: explicit capability memory, without active diagnostic experiment selection.
  4. Full V3-style method: capability memory, goal-conditioned probes, and a harness developed through the declared adaptation protocol.

Control backbone, executor, observation access, compute, and physical interactions. Ablate capability memory, active probing, goal conditioning, and persistent harness revision separately. Charge exploration and unsuccessful probes to the same budget.

  • Does discovery matter? Compare goal-only evaluation with an evaluator-supplied plan diagnostic on paired instances. Keep privileged diagnostics off the main leaderboard.
  • Does a self-model help? Compare against capacity-matched generic memory, then test whether improved capability predictions lead to better final outcomes.
  • Is the improvement compositional? Hold primitive difficulty comparable while changing dependency structure, resource visibility, and alternate-route availability.

Oracle plans and reliable-skill variants help localize bottlenecks; they do not prove a clean reasoning/control decomposition. Report failures from incomplete exploration, incorrect affordance inference, infeasible plans, execution breakdown, and ineffective recovery with observable evidence.

13

Build a small, credible evaluation before expanding coverage

  1. Gate 1 · Select the physical substrate.Choose one simulator and embodiment after checking contact mechanics, object properties, generic skills, sensors, reset fidelity, and verifier isolation. The V3 platform shortlist is a starting point, not a benchmark implementation decision.
  2. Gate 2 · Author composite development families.Start with a small pilot, such as 3–5 families. Establish internal feasible solutions, meaningful discovery, and more than one route where intended. These are planning targets, not completed tasks.
  3. Gate 3 · Audit the contract.Check for goal/API hints, hidden-state leakage, shortcuts, impossible instances, unstable physics, and route-biased grading. Replay independently and validate physical outcome predicates.
  4. Gate 4 · Lock splits and run baselines.Separate task graphs before expanding assets and seeds. Measure skill reliability and budget sensitivity; verify the benchmark distinguishes the intended mechanisms.
  5. Gate 5 · Release reproducible artifacts.Publish environment versions, public task contracts, development assets, interface schemas, metrics, baseline configurations, and replay tools. Maintain a controlled held-out evaluator.

Initial scope: simulation, one embodiment, composite single-agent tasks, and separate track results. Multi-agent cooperation, physical hardware, and wider embodiment coverage are later extensions. No fixed dataset size, simulator choice, success rate, or release date is claimed.
