Research proposal · v6

Can a coding agent get a robot to
work out its own solution?

Embodied Terminal-Bench gives an agent a goal, one or more robots and a physical world it can interact with. Using only the robots' own sensors, the agent writes code, runs experiments and discovers what objects are good for, over hours of iteration, to complete long-horizon tasks. Version 6 keeps the research framing of v5, adopts the settled task design, acceptance, sandbox, scoring and evaluation protocol, and updates the actual progress of every task and executor.

02 · Question and scope

Terminal-Bench, moved into the physical world

VLAs, whole-body controllers and atomic skills provide execution; the coding agent observes, reasons about physics, runs experiments, composes programs and recovers from failure. The target coverage is humanoids, manipulators, quadrupeds and multi-robot teams; the first tasks focus on humanoids and multi-robot teams.

Core hypothesis: with the same executors, observations and budget, an agent that can write and debug programs handles multi-step physical problems better than a direct VLA or an agent that only calls fixed skills, and a reusable harness spreads the cost of exploration over later tasks. Both claims need experiments.

How this page relates to the others

  • This page: research questions, evaluation tracks, experiment design, task taxonomy and progress, roadmap.
  • Specifications: how tasks are designed and accepted, how the sandbox isolates the agent, how scoring works and how evaluations are run, each on its own page: task design, task acceptance, isolated sandbox, scoring and verification, evaluation protocol.
  • Progress details: on the implementation status page.
  • Scope: this is a research and engineering proposal. No LLM agent has been run yet, and there are no formal experimental results.

03 · Three research questions

Three research questions and how each could be refuted

QuestionComparisonWhat would refute it
RQ1 · Does a coding agent help with complex robot tasks?Direct VLA, fixed-skill calls by the same reasoning model, a programmable agent, and an agent that can revise a persistent harness; matched executors, sensors, tasks and budgets; compare valid success, recovery rate and timeGains appear only with stronger executors, more retries or longer budgets; with matched skill coverage, the coding group's success–cost curve does not improve
RQ2 · How can physical reasoning be tested in a sandbox?Write decisions as a "hypothesis → prediction → probe → update → act" loop; compare observation only, random probes on the same budget, informative probes, and removed feedback; record success probabilities and constraint predictions before actingExplanations get more complete but prediction calibration, probing efficiency or final success do not improve; reasoning depends on leaked hidden state
RQ3 · Does self-modelling help across bodies?Fix the world and change reach, gripper, torque or locomotion; compare no memory, general memory of equal capacity, explicit capability memory, and an upper bound with full capability information; difficulty layer 2 tests the same thing inside the sceneGeneral memory of equal capacity explains all the gain; the self-model only remembers robot names

The direct VLA is a system-level reference; causal evidence that code helps comes from the call-versus-program ablation with the same model and interface.

04 · Evaluation tracks

Three tracks: solve, reuse, light adaptation

TrackWhat is allowedHow it is evaluated
A · Solve within the episodeFixed executors and task-provided tools; the agent writes code and runs experiments without changing weights; cross-task memory is cleared for every test instanceThe main track. After the development session the delivered program is re-run on new sealed episodes; see section 02 of the evaluation protocol
B · Build a harness, then freeze and reuse itPerception wrappers, skills, parameter estimation and scheduling code built up over development tasks; skills only from designated sources, preferably rollouts the agent produced itselfFrozen before the hidden test; development and test costs reported separately, with amortised cost = (development cost + N test costs) / N and N stated
C · Light adaptationSmall adapters, calibrators or skill fine-tuning declared in advance; trainable parameters, data volume, update steps and GPU time publishedTotal budget matched to a no-update control; ranked separately and never mixed with training-free results

"Training-free" means no weight updates inside this benchmark; it does not mean the pretrained controllers cost nothing to train. Persistent changes to code and skill libraries also count as learning and must be versioned. A complete solution may not be packaged as a public skill.

05 · Agent, harness and executors

The agent only sees sensors and only commands joints

The structure is the same as in v5: agent → editable harness → frozen executors → trusted simulation → verifier. Version 6 implements it as the H1 isolated sandbox.

  • Isolation: the agent runs in a Linux container (uid 1000, read-only root file system, --cap-drop ALL, internal network) and talks to the environment side only through token-authenticated RPC. Eight methods: info, status, observe, command, command_sequence, declare_infeasible, finish, and reset, which exists only in development mode.
  • Sensors: only the robot's own cameras (RGB and depth), LiDAR, IMU and joint readings. Genesis 1.4.3 has no ray sensor, so the LiDAR is stitched from four depth cameras. No coordinates, object poses, physical properties, segmentation or affordances.
  • Tools: L1 is GR00T WBC standing and walking; L2 is trajectory planning to a target; L3 is IK/FK solving through intermediate points; a VLA is added when the task provides one. Their inputs can only be the agent's own sensor results, and the agent may also write everything itself.
  • Skills: the skill interface is optional. Only skills designated by the task, and skills and rollouts the agent produced in its own development session, may be used; the environment side checks their origin against observation digests.

Details are in section 03 of the isolated sandbox; the feedback the agent receives is in section 05 of the isolated sandbox.

06 · Execution fallback and skills

When skills fall short, solve level by level, then distil what worked into skills

LevelWhat it doesOn failure
L1 · Call an existing skillPick a verified skill from the frozen library and check its preconditions, target range and termination conditionsEscalate to L2 within the remaining budget
L2 · Solve a trajectory directlyGiven the current state, a target pose and obstacle geometry the agent estimated itself, a solver searches for a trajectoryReturn an observable diagnosis and move to L3
L3 · Write intermediate statesThe agent supplies waypoints, contact phases and constraints; each segment is solved with IK/FK and the segments are joinedChange the waypoints or constraints; stop when the budget runs out

L1–L3 here are execution fallback levels, a separate axis from the three difficulty layers.

The distillation loop

  1. Save. After a successful execution, save the solver code, parameters, states, actions, contact events and result.Success on the original task is only where a candidate skill starts.
  2. Parameterise. Prefer extracting the solving program, for example lift_box(box_pose, box_size, lift_height), which regenerates motion for new parameters; with only a trajectory, segment it into templates at contact events.
  3. Validate. Replay on held-out initial states, target positions, box sizes and physical variations, with perturbations.
  4. Register. Only validated skills are registered, with a version, the bodies they apply to, parameter ranges, preconditions and termination conditions; from then on L1 reuses them directly.

Showing it is a skill, not a cached trajectory

  • Compare fixed L1, L1+L2, L1+L2+L3, and skill distillation on and off; add a raw trajectory cache as a control, with controllers, observations and total budget fixed.
  • Report the candidate pass rate, success on unseen parameters, later reuse counts, fallback frequency and amortised time.
  • Graded episodes start from random initial states, so replaying a rollout earns nothing.

Progress: L2/L3 are implemented on a MuJoCo kinematic copy but are not yet connected to physical execution, and there is no skill registration yet. Next: a Genesis native planner or cuRobo backend, solving with orientation and contact constraints, and a trajectory-tracking executor.

07 · Observation and tool use

No stated affordances, only on-board sensors

API calls and physical tool use are different things. The semantics of the interface are public; which objects can serve as tools, how to combine them and which route works are never told to the agent. Objects carry neutral IDs, and the instruction states only the goal and the public compliance constraints; see section 02 of the task design guide.

  • Only sensors native to the robot or that could be fitted to it, with model, mounting pose and noise written into the task card; see section 08 of the task design guide.
  • Contact, force/torque or tactile sensing are optional extensions, with their body locations and noise declared.
  • Text descriptions generated from ground truth belong only to a separate diagnostic condition, never to the main comparison.

The capability-information axis

The Explicit / Partial / Latent capability-information settings from v3 and v5 remain a separate experimental axis, reported apart from the difficulty layers and sensor sets: Partial for the main comparison, Latent for discovery diagnostics, Explicit as an information upper bound. The Harbor CPU version of H1 already implements these three settings (Harbor version notes).

08 · Difficulty and randomisation

Exactly three layers, each adding to the last

LayerWhat the scene containsWhat it testsIn v5
Layer 1Only the necessary tools and objectsDiscovering uses, ordering steps, executingL0
Layer 2Adds tools or objects this robot cannot use but another body couldSelf-modelling: knowing what it can and cannot doNew; tied to RQ3
Layer 3Adds distractors: beyond the robot's capability, not actually usable, or useful-looking but bound to failExperimenting and ruling options outL0.5, L1, L1.5

The v5 L2 grade (weakened grippers, degraded sensors, action noise) is no longer a layer of its own: noise and physical variation go into initial-state randomisation, and faults become separately labelled robustness variants.

  • Randomisation: randomise everything that can be randomised, without breaking solvability, opening shortcuts, or making the key to the solution knowable only from ground truth; see section 04 of the task design guide.
  • Subtasks: completion conditions defined by state, each with a start state from which it can begin on its own, for curriculum learning and diagnosis; subtask scenarios are never offered to the agent under evaluation; see section 06 of the task design guide.
  • Difficulty target: a strong coding agent needs more than 4 hours of iteration. If a difficulty trial solves layer 3 within 4 hours, deepen the dependencies, widen the randomisation, or use distractors that are harder to tell apart.

10 · Cross-embodiment and self-modelling

Fix the world, change the capabilities

Goal, world, resources and budget stay fixed; only the body, the end effector or a validated controller capability changes. The question is whether the agent forms beliefs about itself and the world from evidence, and chooses resources and strategies accordingly.

  • Capability memory records what can be done under which conditions, with predictions, confidence, evidence and failure conditions. One failure is not automatically a body limit: mass, friction, perception and control error are competing explanations.
  • Clean interventions: change one of reach, gripper opening, torque or locomotion at a time, by actually modifying geometry, dynamics or control configuration and re-validating, not by editing a description field.
  • Four kinds of control: the route must change; only an efficiency preference changes; the same route still works; no feasible solution exists (the agent should declare it infeasible).
  • Difficulty layer 2 is the same idea inside a scene: the body stays the same, and the scene contains tools another body could use, testing whether the agent knows it cannot use them.
  • Generalisation is held out by body family, object geometry, mechanism and layout; world-only interventions are kept to test whether the agent attributes failure to itself or to the environment.

11 · Scoring and verification

Scores come only from environment-side records

  • The verifier runs on the environment side and reads trusted state logs, never the agent's own account; the agent never sees its score. See section 02 of scoring and verification.
  • Stage predicates require contact evidence, object identity, dwell times and rest conditions; stages earn process credit, each episode scores its peak, and success (0/1) is reported separately. See section 03 of scoring and verification and section 04 of scoring and verification.
  • Success is still defined as ValidSuccess = goal reached ∧ contract satisfied ∧ integrity passed; an integrity alarm voids the episode.
  • Monitor rules are frozen in advance and grading is fully automatic; people watch recordings only during task acceptance, to check the task and the verifier themselves. See section 05 of task acceptance.
  • Tool understanding is not inferred from final success: diagnostic episodes record predictions about uses and properties, then remove a tool, swap properties or change the body to see whether plans and execution change accordingly. Diagnostics serve research analysis only and do not enter the main score.

12 · Budget, cost and speed

Budgets count simulation steps and tokens; time is only reported

  • Main budgets: simulation steps counted on the environment side and tokens metered by a trusted proxy; observations and resets have their own limits; wall-clock time only guards against hangs. See section 01 of the evaluation protocol.
  • Budget curves: delivery snapshots are scored at budget points to draw success–budget curves, without picking the best seed again at each budget. See section 02 of the evaluation protocol.
  • Speed: reported as a secondary metric: cold-start time, warm solve time, simulated time and total compute cost; Track B reports amortised cost with N stated; for multi-robot runs, wall-clock saved by parallelism is reported together with the extra total work.
  • Measure the base first: the executor's closed-loop ceiling, simulation throughput, model-call latency and reset cost come first, then the affordable task scale. H1 takes about 0.67 s per control step when the GPU is busy with other jobs, which is one reason wall-clock time is not a main budget.

13 · Experiments and baselines

Show that coding helps before scaling up

ConditionWhat it isWhat it answers
B0 · Direct VLAThe same frozen VLA, given the goal, with normal feedbackEnd-to-end system reference; unsupported bodies listed separately
B1 · Fixed-skill agentThe same reasoning model, perception and skills, calling one step at a time with no free-form programsThe ablation control for RQ1
B2 · Coding agentThe same interface, with code, loops, branches and debugging allowedWithin-episode gains (Track A)
B3 · Reusable harnessB2 plus cross-task skill building during development, then frozenDevelopment and amortised gains (Track B)
No-opDoes nothingLower anchor; must score 0
Reference expertThe expert solution that reads ground truthUpper anchor; proves solvability and validates the verifier
Simple script (optional)A fixed script that only uses task-provided skills and does no perceptionWhether a fixed routine can score on the task

The standard agent configuration (a pinned coding agent with a default prompt) is one instance of B2, and it is the configuration used for difficulty trials in the contribution process; see section 05 of the evaluation protocol.

  • Repeats: three independent evaluations per agent and task; every delivery scored three times on the same sealed episodes and averaged; paired bootstrap confidence intervals over task and scene clusters. See section 04 of the evaluation protocol.
  • Ablations: RQ2 runs observation-only, random-probe, informative-probe and removed-feedback variants of B2; RQ3 compares no memory, general memory and a self-model under the same storage, token and trial budgets.
  • Decision rules: if scripts cannot execute reliably, fix the executors first; if coding does not improve valid success at matched budgets, analyse failures and costs instead of adding tasks to support the claim; if gains come only from seen routes, hold out mechanisms and bodies rather than adding in-distribution variants.

14 · Curriculum and extensions

Subtasks support a curriculum; new tasks must pass acceptance

  • Curriculum: atomic-skill baselines → single uses (support, push, extended reach) → composed preconditions → the final goal after freezing → the next development round. Subtask start scenarios let each step be practised and measured on its own.
  • RSI-WM: "choose an experiment → gather physical evidence → revise the harness → improve the final task" as a curriculum loop; the world model can be a structured belief or a bounded predictor, with no requirement to train a video world model.
  • Data flywheel: its gains must be measured: valid-trajectory rate, behavioural diversity, cost per valid trajectory, and downstream success at the same data volume; all augmented trajectories are re-validated.
  • Generated tasks: may propose candidates, but must pass task acceptance before admission.
  • Extensions: deformable objects (cloth, bags, ropes) need matching simulation, controllers and predicates; the first tasks do not depend on them.

16 · Roadmap and scope of v6

Where things stand and what comes next

  1. G0 · Reproduction and selection. The three WBCs, SONIC and N1.7 passed short tests in local simulation; the L2/L3 solvers are implemented.Open: box-level manipulation exists only in the official example.
  2. G1 · Trusted bridge. The H1 isolated sandbox is implemented: escape probes, sensor geometry, checkpoint restore and grading mode are verified with scripted agents.Open: no LLM agent has been run; the scoring and monitoring to-do items are on the status page.
  3. G2 · Executable tasks. H1 first: the expert direct family at 10/10 and the stool chain completed 3 times; the light M2 setup solved.Next: reorganise H1 into the three layers, solve carrying the stool, and complete acceptance; build reference experts for the other tasks.
  4. G3 · Minimal comparison. Run B0–B3 and the baselines; report budget curves, failure attribution and executor coverage; answer RQ1 first, then RQ2 and RQ3.
  5. G4 · Curriculum and generalisation. Add body and end-effector changes, frozen skill libraries and mechanism hold-outs, and test the data gains; more bodies and deformable objects follow one at a time.

Version 6 delivers this proposal in English and Chinese together with the specifications on the other pages. No model has been trained and no formal experiment has been run on this benchmark; public material must keep design goals, implementation coverage and measured results apart.
