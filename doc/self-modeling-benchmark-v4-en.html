01

Terminal-Bench for embodied agents

Give an agent a goal, one or more bodies, and an interactive physical world. Let it write code, discover tool uses, compose skills, and revise its harness to solve long-horizon tasks.

Version 4 centers on tool use + coding + harness writing, under the working name Embodied Terminal-Bench. VLAs, whole-body controllers, and atomic skills supply execution capabilities; the coding agent observes, reasons, experiments, composes programs, and recovers. Target embodiments include humanoids, manipulators, quadrupeds, and robot teams. The initial tasks belong to Tool Discovery, with Humanoid and Multi-Robot as embodiment labels. Dual G1 long-object transport (M2 / Version B), G1 cart-assisted heavy object transport (H2 / Version C), G1 self-closing door traversal (H3 / Version D), and G1 ramp/bridge construction (H4 / Version E) are prioritized as P0. High-shelf retrieval via improvised robot tool use (M3 / Version F) adds a P0/P1 creative tool-use and cooperation task. Lever-assisted heavy object lifting and transport (H5 / Version G) adds a P1 mechanical-advantage and multi-stage tool-composition task. Dual-quadruped transport (M4 / Version H) adds P0 cooperative towing with Go1/Go2 robots.

Core hypothesis: with matched executors, observations, and budgets, program-writing agents outperform direct VLAs or fixed-skill callers on multi-step physical problems. Reusable harnesses may amortize exploration over subsequent tasks. Both claims require experiments.

Change from v3: capability discovery and self-modeling become the mechanism study in RQ3; the primary question is whether coding agents help robotics. Training is off by default, with separately budgeted light training as an option. Deformables are an extension. Lower latency is a design objective; we do not assume that existing approaches are uniformly slow.

This is a research and engineering proposal. Benchmark interfaces, budgets, tasks, and experiments await implementation; see controller validation status for standalone simulation progress, which does not establish task feasibility. Benchmark v3 and the V3 method proposal [external workspace] remain separate.

02

Three research questions and falsifiable tests

RQ1 · Do coding agents help with complex robotics tasks?

Compare direct VLA control, fixed-skill calling with the same reasoning model, programmable agents, and agents that persistently revise a harness. Match skills, sensors, tasks, token caps, and interaction budgets; measure valid success, recovery, and latency. Direct VLA is a system baseline. The causal test of coding uses the same model and interface in calling-versus-programming ablations.

Falsifier: gains require a stronger executor, more retries, or longer budgets; the success–cost curve does not improve after skill coverage is matched.

RQ2 · How can a sandbox test physical reasoning?

Define the robot brain operationally: hypothesis → prediction → probe → update → execution. Compare observation only, budget-matched random probes, informative probes, and removed-feedback variants. Record success probabilities and constraint predictions before acting; use world-property interventions and execution outcomes to assess useful updates.

Falsifier: richer explanations fail to improve calibration, probe efficiency, or final success, or predictions depend on leaked hidden state.

RQ3 · Does self-modeling improve cross-embodiment adaptation?

Hold scene and goal fixed while changing reach, gripper, torque, or validated mobility. Compare no persistent memory, equal-capacity generic experience memory, explicit self/world capability memory, and an oracle-information diagnostic ceiling. Measure plan adaptation, capability calibration, and sample efficiency.

Falsifier: generic memory explains all gains, or the self-model memorizes robot names and fails on new bodies, irrelevant changes, or cases requiring no strategy change.

03

Three tracks: solving, reuse, and light training

A / SOLVE

Program within an episode

Freeze the VLA/controller and public skills. Agents write code, branches, loops, local memory, and recovery logic without weight updates. Reset cross-task memory for each test instance; charge every permitted retry within the episode.

B / BUILD A HARNESS

Develop, freeze, reuse

Build perception wrappers, skill composition, parameter estimation, failure detection, and scheduling code on development tasks. Submit source, locked dependencies, documentation, and a skill-library snapshot. Freeze before hidden evaluation; report development and test costs separately.

C / LIGHT ADAPTATION

Optional bounded learning

Allow only declared small adapters, calibrators, or skill fine-tuning. Publish trainable parameters, data volume, update steps, and GPU time. Match total budgets against a zero-update control; rank this track separately.

Training-free means no weight updates during this benchmark, not zero pretraining cost. Persistent code or skill-library changes are also learning and must be versioned. Public atomic skills cannot encode complete task answers; composed skills must arise from permitted development experience.

04

Robot brain, harness, and executor

Separate slow reasoning from fast control. The agent decides at skill boundaries or failure events while a frozen controller maintains the control loop. On LLM timeout, the executor enters a validated hold/stop state. Language subgoals need typed objects, poses, contacts, durations, and termination conditions. Missing controller skills are explicit coverage gaps.

Candidate public primitives are observe, navigate, reach, grasp, place, push, and validated step. Handoffs compose explicit actions and synchronization for both robots. Publish each body/controller's supported interfaces, units, frames, valid parameters, and observable errors; hidden call syntax is not the task.

05

Withhold tool-use hints; specify observations and interfaces

Separate API tool calling from physical tool use. API semantics are public. Which scene objects serve as tools, how to combine them, and which route works are undisclosed. Use neutral object IDs without correct_step_box, purpose labels, or solution graphs. Instructions state only the goal and public validity constraints.

Agents observe appearance, spatial relations, and permitted physical feedback to infer load bearing, friction, movability, graspability, and support. Discovering that an object can become a step is different from knowing the argument format for step. Disallow task-specific solve_shelf() primitives; allow transferable motion, contact, and grasping skills.

Vision

Base RGB plus proprioception; RGB-D is an explicit sensor variant with resolution, rate, latency, and calibration recorded. Do not silently add exact simulator object poses to the visual track.

Contact and touch

Optional force/torque, contact, or tactile sensing with declared body coverage and noise. Record missing sensors separately from degraded signals.

Text grounding

Describe objects using the permitted perception pipeline, with provenance and confidence. Ground-truth-derived text belongs in a separate oracle track. Descriptions must not recommend object uses.

Retain v3's Explicit / Partial / Latent capability disclosure as an independent axis, separate from difficulty and sensor configuration. Use Partial for the proposed main comparison, Latent for discovery diagnostics, and Explicit as an information ceiling.

06

Difficulty curriculum: affordances to uncertain execution

  1. L0
    Every candidate object has a useful role

    No distractors; reliable properties. Agents still select, order, and invoke skills. Useful does not mean mandatory, and object-purpose instructions remain absent.

  2. L0.5
    Non-obvious uses / changed properties

    Similar appearances hide different heights, friction, or load bearing; familiar objects may be repurposed. Infer from observable evidence or budgeted interaction.

  3. L1
    Useful objects mixed with irrelevant ones

    Add distractors. Choosing not to use an object can be correct. Preserve a feasible route rather than merely increasing visual clutter.

  4. L1.5
    Apparently useful traps

    Examples include slippery supports, tipping boxes, or resources that lead to dead ends. Provide obtainable evidence or probing opportunities; allow uncertainty when alternatives are indistinguishable.

  5. L2
    Adversity, faults, and uncertainty

    Introduce weaker grippers, degraded sensors, action noise, or controlled disturbances. Test one factor before combinations; require failure detection, recovery, or justified stopping.

We label the additional L1 difficulty in the notes L1.5 to distinguish it from L0.5. Levels are curriculum labels, not an empirically established ordering. Validate them through failures and cost. Keep traps, properties, faults, and observation noise separately tagged rather than attributing every failure to reasoning.

Current task taxonomy: nine tasks, four goal families

Tool Discovery remains the umbrella category. Group tasks by their primary goal to compare related problems across bodies; record physical mechanisms, embodiment, and implementation status as separate tags. Keep IDs H1–H5 / M1–M4 and the existing directories unchanged.

1 · Elevated retrieval and reach extension

H1, M1, M3. Extract and deliver a target that is not directly accessible. Mechanisms include support construction, container repositioning, complementary robot roles, and lifting or supporting another robot as a tool. M1 emphasizes role allocation and handoff; M3 emphasizes discovering a robot's use as a tool.

2 · Heavy / long-object transport

H2, H5, M2, M4. Overcome payload or geometric limits to deliver an object. Mechanisms are cart support, lever mechanical advantage and support transfer, load sharing between two G1s, and coordinated quadruped towing with tension control.

3 · Dynamic obstacle management

H3. Manage a passage constraint that restores itself during transport. Key mechanisms are holding a door open, checking tool effectiveness, and sequencing opening, tool placement, regrasping, and traversal.

4 · Route construction and terrain modification

H4. Assemble materials into a traversable structure, then retrieve or deliver an object. Key mechanisms are ramp / bridge construction and stability under combined loads. Beyond H1's local reach extension, this family requires validating a complete traversable route.

Version G — G1 Lever-Assisted Heavy Object Lifting and Transport

H5 · P1 · Tool Discovery · Humanoid · Specification only

A single Unitree G1 must move a heavy box beyond its direct lifting capacity to a designated region. Long rods, fulcrum blocks, shims, rollers, and other interactive objects are available without tool-use instructions. The agent must discover how to change the force conditions to lift and transport the load.

  • Discover the G1's lifting capability, grasp limits, and the box's mass distribution through physical interaction to diagnose why direct carrying is infeasible.
  • Independently discover that a rod and a fulcrum can form a lever. Select fulcrum position, effort location, and contact angle to raise one side of the box with a smaller applied force.
  • Explore using shims, support blocks, or rollers after staged lifting to support the box and complete transport by rolling, pushing, or repositioning.
  • Independently write a multi-stage control harness coordinating tool grasping, fulcrum placement, contact adjustment, force control, temporary support, roller insertion, and heavy-object transport.
  • When the lever slips, the fulcrum becomes unstable, force is insufficient, or the box tilts, diagnose the failure from feedback and revise the lever arrangement, contact positions, or transport strategy.
  • Advanced variants: vary box mass and center of mass, lever length and stiffness, fulcrum friction, G1 effective force capability, and tool combinations. Retain at least one physically validated executable solution per admitted solvable instance; test discovery of mechanical advantage, multi-tool composition, and control-program reconstruction.

Core capabilities: Autonomous Tool Discovery · Lever and Torque Reasoning · Mechanical Advantage · Multi-Stage Tool Composition · Harness Construction · Embodied Self-Modeling · Long-Horizon Planning

Implementation gate: validate the direct-lifting limitation and the complete tool-handling, edge-lifting, support-transfer, and transport chain. Check contact geometry, effective lever arms, grasp retention, robot torque and balance, lever travel, friction, and fulcrum stability. Mechanical advantage must arise from physical contacts and moments; stiffness variants require modeled compliance. Raising one edge alone is insufficient. Candidate strategies are design examples, not agent instructions.

Environment implementation and physical feasibility validation are pending. H5 task specification and implementation checklist.

Version E — G1 Ramp / Bridge Construction

H4 · P0 · Tool Discovery · Humanoid base · Specification only

A single Unitree G1 must retrieve a target object from beyond an obstacle or transport it to a designated region, but the route contains a step, gap, or height difference that the robot cannot cross directly. Planks, boxes, and support blocks are available without predefined tool roles. The agent must discover how to construct a traversable route.

  • Assess the G1's stepping capability, reach, and obstacle geometry to identify why direct movement cannot complete the task.
  • Explore the potential uses of planks, boxes, and supports. Measure or estimate length, stiffness, load-bearing capacity, and friction through permitted observations and interaction to judge whether a ramp or temporary bridge is feasible.
  • Independently synthesize a tool-composition and environmental-construction harness that coordinates material transport, support placement, plank positioning, structural stability checks, and subsequent traversal.
  • If a ramp is too steep, a plank slips, or the support structure is unstable, use physical feedback to revise the structure, change the material combination, or replan the route.
  • Advanced variants: vary gap width, step height, plank length and stiffness, support stability, and the G1's effective stepping capability. Some instances require multiple objects. Add quadruped or wheeled-robot variants to test redesign for different bodies. All official instances labeled solvable must pass physical simulation validation.

Core capabilities: Autonomous Tool Discovery · Physical Reasoning · Environmental Construction · Harness Synthesis · Embodied Self-Modeling · Cross-Embodiment Adaptation

Implementation gate: validate the complete material-handling, assembly, stability-testing, traversal, and retrieval/delivery chain for the assigned body and controller. Retrieval includes the return path with the target. Check slope, support contacts, friction, deflection, and the combined robot–object load. Stiffness variants require modeled compliance; quadruped and wheeled variants require validated manipulation and locomotion capabilities. Candidate constructions are design examples, not evaluation hints.

Environment implementation and physical feasibility validation are pending. H4 task specification and implementation checklist.

Version D — G1 Self-Closing Door Traversal

H3 · P0 · Tool Discovery · Humanoid · Specification only

A single Unitree G1 must carry a box from room A to room B through a self-closing door. The G1 can open the door, but cannot keep holding it open while carrying the box with both hands. Wooden wedges, heavy objects, and other interactive objects are available; the agent must independently discover how to keep the door open.

  • Discover the door's closing mechanism through interaction, diagnose why direct transport fails, and explore which objects can serve as temporary holding tools.
  • Use a wooden wedge, a heavy object, or another object to prevent closure, while verifying placement, friction, and the resulting holding effect.
  • Independently write a long-horizon control harness to coordinate opening the door, placing a tool, checking the door state, regrasping the box, traversing the doorway, and placing the box at its destination.
  • If the door cannot remain stably open, use execution feedback to adjust the tool, its placement, or the passage sequence instead of repeating a failed strategy.
  • Advanced variants: vary closing force, friction coefficients, doorway width, box dimensions, and tool properties. Include ineffective wedges or heavy objects that slide easily. Retain at least one physically executable solution per admitted configuration, and test whether the agent recognizes tool failure and reconstructs its control program.

Core capabilities: Autonomous Tool Discovery · Physical Affordance Reasoning · Environmental Modification · Harness Construction · Long-Horizon Planning · Failure Recovery

Implementation gate: validate opening, two-handed carrying, physical tool placement, stable door clearance, and the complete release–regrasp–traversal sequence. The box must reach room B through continuous physical execution and be placed stably. Tool holding must arise from contact physics, not a scripted door lock. Candidate tools and strategies are design examples, not evaluation hints; valid alternative routes receive credit.

Environment implementation and physical feasibility validation are pending. H3 task specification and implementation checklist.

Version C — G1 Cart-Assisted Heavy Object Transport

H2 · P0 · Priority implementation · Specification only

A single Unitree G1 must transport a heavy box beyond its direct carrying capacity to a designated target region. A movable cart is available, but the route includes narrow passages, so simply pushing the box in a straight line cannot reach the goal.

  • The G1 cannot lift the box directly. The agent must discover its payload limit through physical interaction and independently recognize the cart as an auxiliary transport tool.
  • The agent explores loading methods such as pushing, tilting, lifting in stages, or using environmental supports, without assuming that the robot can directly lift the entire box.
  • The agent independently writes a cart-control harness that coordinates the G1's movement, pushing force, contact location, and cart motion for stable transport.
  • In narrow passages, adapt to cart dimensions, box orientation, turning radius, and the G1's mobility. Reposition, change pushing direction, or make repeated pose adjustments when needed.
  • Advanced variants: vary box mass, cart payload capacity, wheel friction, passage width, and robot pushing-force limits. Every admitted variant must retain at least one physically executable solution. Test whether the agent discovers tool-use conditions, diagnoses control failures, and modifies its harness.

Core capabilities: Autonomous Tool Discovery · Physical Reasoning · Harness Construction · Load and Mobility Constraints · Embodied Self-Modeling · Long-Horizon Planning

Implementation gate: validate the direct-lifting limitation and a feasible loading route, followed by contact-driven cart motion, stable transport, passage negotiation, and delivery. Check load capacity, wheel behavior, contact forces, balance, and clearance for the robot, cart, and box. Candidate strategies are design examples, not evaluation hints. The cart moves through robot contact; direct cart actuation cannot bypass the G1's capability limits. Unless explicitly required, unloading is not part of the delivery goal.

Environment implementation and physical feasibility validation are pending. H2 task specification and implementation checklist.

H1 — Build Support and Retrieve a Shelf Box

“Move the target box from the shelf to the designated receiving area.”

Body and scene
G1 or another humanoid; an elevated target, movable boxes/platforms, floor, and receiving area. Bodies share the same goal, scene, and resource set. Start with rigid objects.
Hidden affordance
Boxes may become supports or steps. The agent decides whether they are needed, which to use, how to arrange them, and how to recover. Instructions never prescribe stacking or climbing.
Candidate chain
Observe target → estimate own reach → assess movability/load bearing → transport and arrange → step stably → grasp → deliver. Every transition requires executable control. Other valid routes, including direct retrieval, earn credit.
Body variants
A high-reach body may retrieve directly, another may need one support, and a shorter body may need two boxes arranged as accessible steps or a stable stack. Both boxes remain present across variants; resource counts do not reveal the answer.
Admission checks
Validate foothold area, step height, center of mass, box contacts, load bearing, friction, grasping, and ascent/descent transitions. Sufficient combined box height does not establish climbability.
Success contract
The robot delivers the target into the receiving area for a predefined dwell time while respecting public fall, damage, and contact constraints. Verify continuous simulated motion without teleportation, state edits, or contact bypasses.

Executor gate: independently reproduce box transport, stable stepping, grasping, and descent before agent evaluation. If G1 stepping is unsupported, label that configuration unready. A fixed platform can debug the interface but cannot count as solved tool construction.

Version H — Dual Quadruped Cooperative Long-Object Transport

M4 · P0 · Tool Discovery · Multi-Robot / Quadrupeds · Specification only

Two Unitree Go1/Go2 robots must cooperatively transport a long cargo box to a designated region through narrow passages and a 90° L-shaped corridor. Without manipulators, they cannot directly grasp the cargo. Ropes, towing connection points, a drag platform, and other interactive objects are available. The agent must discover a feasible towing arrangement and write the cooperative control program.

  • Discover each robot's towing capability and mobility limits, as well as cargo mass, friction, and geometry, through physical interaction. Assess whether a single robot can complete transport.
  • Independently discover how ropes, towing connection points, or a drag platform can form a transport arrangement. Explore how connection locations affect cargo direction, rotation, and stability.
  • Write a multi-robot harness coordinating robot motion, towing direction, relative position, and rope tension for stable transport.
  • At the L-shaped corner, jointly plan cargo translation and rotation by adjusting towing directions, speeds, and formation to avoid severe collisions or connection failure.
  • Diagnose stuck cargo, slack ropes, insufficient towing force, or unsynchronized motion from feedback; revise towing strategy, motion order, or the harness.
  • Advanced variants: vary cargo length, mass, center of mass, ground friction, corridor width, and effective towing capability. Include unequal robot capabilities requiring discovery and dynamic allocation of primary pulling and steering roles. Retain at least one physically validated solution per admitted solvable instance, and test adaptation of connections, cooperation, and control code.

Core capabilities: Multi-Robot Coordination · Autonomous Tool Discovery · Cooperative Towing · Physical Reasoning · Harness Construction · Embodied Self-Modeling · Long-Horizon Planning · Failure Recovery

Implementation gate: specify initial connections and physically executable attachment, release, reconnection, and platform-use operations. No manipulators means rope grasping, knot tying, or loading cannot be assumed. Preconnected scenes validate towing, not autonomous attachment construction. Validate rope slack/tension, traction, connection loads, robot stability, and clearance through the complete route. Credit valid solo routes and verify when cooperation is necessary. Candidate strategies are design examples, not agent instructions.

Version F — G1 High-Shelf Retrieval via Improvised Robot Tool Use

M3 · P0/P1 · Tool Discovery · Multi-Robot · Specification only

A Unitree G1 must retrieve a small ball from a box on a high bookshelf and place it in a designated region. Target height and a limited opening make precise direct grasping difficult. Candidate step boxes and a small wheeled robot with a manipulator are available. The agent controls both robots without a predefined tool-use plan or cooperative program.

  • Explore shelf height, container opening, target position, and the G1's reach, grasp precision, and stability to assess direct-grasp feasibility.
  • Solution A — Box-Assisted Retrieval: discover and use boxes to construct temporary steps, increase the G1's effective operating height, and attempt to retrieve the ball.
  • Solution B — Robot-as-a-Tool: discover that the wheeled manipulator is better suited to precision grasping but lacks height or workspace. Explore having the G1 lift or support the lightweight robot to raise its manipulator, then use that arm to grasp the ball.
  • Independently write a multi-robot harness coordinating G1 grasping, lifting, and stable support with manipulator positioning, extension, visual servoing, grasping, and object handoff.
  • Use physical feedback to assess G1 payload, wheeled-robot mass and center of mass, arm workspace, support stability, and grasp precision; select or revise an executable strategy.
  • Advanced variants: vary shelf height, box load capacity, wheeled-robot weight, manipulator reach, and G1 payload. Physically validate at least one feasible solution per admitted solvable instance. Include step-suited, second-manipulator-required, and combined-tool instances.

Core capabilities: Creative Tool Use · Robot-as-a-Tool · Autonomous Affordance Discovery · Multi-Robot Harness Construction · Embodied Self-Modeling · Physical Reasoning · Long-Horizon Planning

Implementation gate: validate complete routes, including step stability, actual grasp/support contacts, combined center of mass, manipulator reactions, visibility, precision grasping, delivery, and stable placement of the supported robot. Robot lifting cannot rely on scripted attachments or frozen bases. Solutions A/B are design candidates, not agent instructions. Credit valid single-robot routes and verify when cooperation or combined tools are necessary.

Environment implementation and physical feasibility validation are pending. M1 remains a separate collaboration task. M3 task specification and implementation checklist.

Version B — Dual G1 Cooperative Long-Object Transport

M2 · P0 · Implement first · Specification only

Two Unitree G1 robots cooperatively carry a long box through a narrow corridor with a 90° L-shaped turn and deliver it to the designated target region.

  • Each G1 handles one end of the box. The agent independently writes the control harness that coordinates both robots.
  • At the L-shaped corner, jointly adjust the box's position and orientation, grasp points, and the robots' relative formation to avoid collisions between the box and the walls.
  • The two G1 robots may have different effective payload capacities, grasp stability, or mobility limits. The agent must discover these capability boundaries through interaction and distribute the load appropriately.
  • When direct carrying cannot negotiate the corner, the agent explores alternatives such as changing grasp positions, rotating the box in stages, or temporarily setting it down and regrasping it.
  • Advanced variants: vary box length, mass, center of mass, corridor width, and robot payload limits. Every admitted variant must retain at least one physically executable solution; test whether the agent discovers the constraints and reconstructs a feasible cooperative control program.

09

Task expansion and the meaning of long horizon

Define long horizon through dependency depth, tool composition, persistent state, and recovery, not video duration or repeated actions. Record critical dependencies, decisions, simulated time, and wall-clock time. Partial progress uses verifiable states without prescribing one reference route.

  • Standard manipulation: transport, pick-and-place, opening, and repositioning establish primitive and end-to-end control baselines.
  • Reasoning-heavy: physical Hanoi, nested containers, and obstruction removal test ordering, temporary storage, and constraints. Correct symbolic plans must still execute physical grasps and placements.
  • Resource construction: box steps, bridges/ramps, or poles change access, subject to real forces, contacts, and traversability.
  • Body coverage: fixed arms establish tabletop tool use; humanoids add support and whole-body transitions; quadrupeds begin with navigation, pushing, or supported arm actions. Grasping is not assumed for every quadruped.
  • Deformables, optional: cloth-assisted retrieval, flexible-bag handling, or rope pulling. Require compatible simulation/control, deformation/contact predicates, and separate throughput measurements. The first release does not depend on them.

Automatic generation may propose objects, goals, and constraint combinations, but cannot directly populate the official test set. Each candidate needs controller feasibility, stability checks, negative scoring examples, solution deduplication, and split review. Successful object teleportation alone is not evidence of robot feasibility.

10

Cross-embodiment self-modeling: fixed world, changed capability

Fix (Goal, World, Resources, Budget) Intervene on Body / End-effector / Validated controller capability Evidence history → self/world belief → resource selection and feasible strategy

Capability memory records what works under which conditions, including predictions, confidence, evidence provenance, and invalidation conditions. Reach depends on posture/support; payload depends on grasp, speed, and stability. One failure does not identify a body limit: mass, friction, perception, and controller errors are competing explanations.

  • Clean interventions: change one reach, gripper opening, torque, or mobility factor first. Modify and revalidate actual geometry, dynamics, or control, not just metadata. Naturally different robot models become later generalization tests.
  • One box / two boxes: compare effective reach in the same scene. Body changes may also alter balance and viewpoint; document these consequences. With multiple solutions, a changed strategy is not automatically a correct one.
  • Four controls: required route change, efficiency-only change, unchanged feasible route, and no feasible route under available resources. Infeasibility labels require a declared validation scope, not merely one agent's failure.
  • Generalization splits: hold out body families, object geometries, mechanisms, and layouts. Renaming, recoloring, and irrelevant hidden changes detect name memorization and unnecessary adaptation.

Retain world-only interventions to test self/environment attribution. Full-capability and ground-truth-state ceilings are separate from fair main comparisons. An explicit self-model is a method hypothesis, not a participation requirement.

11

Stepwise curriculum, RSI-WM extension, and the data flywheel

  1. Establish primitive competence. Use existing controllers and independently measure navigation, grasping, placement, pushing, and available stepping skills. Diagnose execution coverage first.
  2. Learn individual affordances. Explore support, pushing, and reach extension in development scenes; retain conditional skills and failure evidence.
  3. Compose prerequisites. Clear an obstruction before retrieving a tool, or validate support before climbing. Test reusable skills on new layouts.
  4. Freeze and solve final goals. Evaluate unseen combinations, properties, and bodies. Permit only within-track test-episode adaptation; never feed test-verifier outcomes into the curriculum.
  5. Start the next development cycle. Update libraries from trusted trajectories, failures, and code revisions in development/training pools only; freeze another version for independent evaluation.

RSI-WM extension here means the proposed curriculum loop: select an experiment → obtain physical evidence → revise the harness → improve final-goal performance. No external implementation is assumed integrated. The world model can be a structured belief or bounded predictor; a large video world model is not required.

Measure the flywheel: valid-trajectory yield, valid behavior/strategy diversity, cost per valid trajectory, and downstream success with matched data and training budgets. Compare fixed-script randomization and noncurriculum sampling; revalidate every augmented rollout. Prioritize code/skill reuse, then optionally test small-scale VLA data gains through light training. More trajectories alone do not establish improvement.

12

Make speed an evaluation variable

Performance objective: keep pretrained executors controlling continuously while agents plan and debug from a small number of informative observations. Profile executor competence, simulation throughput, model-call latency, image processing, startup, and reset costs before choosing scale.

Reduce repeated overhead

Pin dependencies and warm models; reuse processes with complete episode-state resets; cache generic skills during development. Action chunks and event-triggered observations reduce LLM turns. Preserve critical/failure video and complete trusted state logs.

Match budgets

Cap wall clock, LLM tokens, simulation steps, resets, GPU time, and concurrency. Charge probes, failures, internal retries, code execution, and both robots' work. Do not measure only the final successful video.

Start the pilot with a proposed 5 / 15 / 30-minute success–budget grid. These are calibration targets, not demonstrated speed or real-time guarantees. Use prefixes of the same trajectory and predetermined checkpoints rather than selecting different lucky seeds per budget. Verifiers read offline and never return scores to the solving agent.

Report end-to-end cold-start time, warm solving time, simulated physical time, total compute cost, and amortized cost (development cost + N test costs) / N, stating N. Track B must not hide expensive development behind fast frozen-harness execution. Report both reduced wall time and increased total work for concurrent robot teams.

13

Harbor sandbox and the trusted physics boundary

Use Harbor to orchestrate tasks, agents, and sandboxes, with its separate-verifier mechanism as the evaluation foundation. Container isolation does not guarantee the absence of reward hacking. The following is our proposed protocol, pending implementation and validation.

  1. Agent workspace: mount only public instructions, SDK, permitted dependencies, and writable code. Keep private TaskSpecs, solutions, true properties, hidden seeds, and scoring scripts outside the container.
  2. Trusted simulator worker: own state and physical parameters outside agent permissions. Expose only sensors, actions, and budgeted development resets. Do not forward arbitrary Python evaluation, state setters, file reads, or engine debugging.
  3. Separate verifier: read trusted state logs/trajectories and submitted artifacts. Protect scoring outputs; replay frozen programs in clean hidden instances. Online Track A uses trusted closed-loop traces, and replication reruns the agent.
  4. Minimal reachability: pin dependencies and allow runtime network access only to required model proxies and execution RPC. Exclude host Docker sockets, privileged mode, and scoring mounts; check IPC, process visibility, and error logs for leakage.
  5. Audit with negative cases: test altered clients, fabricated success logs, invalid RPC, scoring-file reads, and cross-episode residue. Independently inspect contact, energy, and continuity anomalies with video review.

Development permits resets, experiments, and public execution feedback. Evaluation permits only declared reset counts and observations. Container controls reduce software tampering and leakage; they cannot automatically detect simulator contact exploits. Evaluate both boundaries separately.

14

Verification: success, tool understanding, and anomalies

Two evidence channels: trusted simulator contracts check object identity, goal regions, dwell time, contacts, stability, and constraints. Synchronized video supports human review of strategies, abnormal contacts, and scoring disagreements. Retain timestamped scene and robot views. Video judgment does not replace state contracts; plausible-looking simulation does not prove real-world physical validity.

Valid unexpected solution

Meets public constraints and goals through continuous physical execution, reproducible under small perturbations and reruns. Novel tool compositions or role allocations need not match a reference route.

Physics / contract exploit

Penetration, anomalous energy, unintended engine behavior, or an end-state score that accepts the wrong object. Flag for review or rejection; exclude from valid successes and positive training data.

Tampering / leakage

Reward-file edits, hidden-answer access, or state-setter calls. Classify violations from access/action evidence without inferring intent from an agent's explanation.

Do not infer tool understanding from final success. In diagnostic episodes, record affordance/property predictions, then remove tools, exchange properties, or change bodies and assess corresponding plans and execution. Explanations are supporting evidence only. Report diagnostic-query tokens and latency separately from the main speed comparison.

  • Primary outcomes: valid success versus budget; paired success differences and confidence intervals. Report tokens, wall clock, GPU/robot work, and cost per valid success.
  • Reasoning and adaptation: recovery after failure, useful-probe cost, capability Brier score/calibration, constraint attribution, and separate accuracy for required switches and appropriate invariance.
  • Behavior audit: valid strategy novelty, exploit/tampering rate, and unresolved-case rate, with denominators. Two method-blinded reviewers independently label novelty/anomalies and adjudicate disagreements.
  • Infrastructure outcomes: separate crashes, timeouts, missing executor skills, and agent failures. Disclose attempted runs and infrastructure failures instead of silently dropping unfavorable samples.

Use ValidSuccess = GoalReached ∧ ContractSatisfied ∧ IntegrityPassed. Freeze thresholds, windows, tolerances, and anomaly handling before evaluation. Report conservative statistics and unresolved counts when validity is undecided. Reference solutions establish feasibility, not a unique acceptable route.

15

Minimum experiment: establish coding gains before scaling

Starting point: prioritize the H2, H3, H4, M2, and M4 executor gates, then complete H1/M1 gates and validate direct/simple, tool-required, and perturbed conditions for each family. Separate development, validation, and hidden-test scenes; related layouts, variants, and trajectories must not cross splits. Small pilot samples diagnose failures and estimate variance; preregister the formal seed count from variance and affordable budgets.

  1. B0 / Direct VLA: the same frozen VLA with goal input and normal feedback, as an end-to-end system baseline. Report unsupported bodies separately rather than substituting unmatched controllers.
  2. B1 / Fixed-skill agent: the same reasoning model, perception, and skills, with sequential calls but no arbitrary programs or persistent harness revisions.
  3. B2 / Coding agent: the same interfaces plus code, loops, branches, and feedback-driven debugging. Track A measures within-episode gains.
  4. B3 / Reusable harness: B2 plus development-time skill accumulation across tasks, followed by freezing. Track B measures development and amortized returns.
  5. Diagnostic references: executable handwritten scripts measure executor coverage; complete capability information provides an information ceiling. Neither enters agent rankings.

On B2, RQ2 ablates observation only, random probes, informative probes, and removed feedback. RQ3 compares no memory, generic memory, and self-models under equal storage, token, and experiment budgets. Add light training, sensor changes, and team scheduling separately after the main effects are established.

Statistical unit: use independent solver seeds on matched tasks, and compute paired uncertainty over task/scene clusters, not video frames. Report each family separately to avoid overweighting long tasks. Hidden tests serve final comparisons; method changes informed by them require a fresh held-out set.

Decision rule: if scripts cannot execute reliably, repair the executor. If coding does not improve valid success at matched budgets, investigate failures and cost before scaling task counts. If gains rely on familiar routes, expand held-out mechanisms/bodies rather than near-duplicate instances.
