## 从初始状态运行

在仓库根目录 `robo-si` 执行。使用已安装本项目 Genesis、MuJoCo、Torch 等依赖及运动策略资源的 Python 环境；环境安装说明见[任务 README](../README.md)。以下为 PowerShell 命令，其中输出目录应每轮使用新名字：

```powershell
$env:OMP_NUM_THREADS = "1"
$env:MKL_NUM_THREADS = "1"
$env:OPENBLAS_NUM_THREADS = "1"
$runDir = "humanoid/g1_support_retrieval/oracle/runs/fresh-repro-01"
python -u -m humanoid.g1_support_retrieval.oracle.stool_chain `
  --out $runDir `
  --seed 2 --carry 1.0 --mass 1.5 --friction 0.5 `
  --walk-mode planned --effort-caps physical --self-collision 0 `
  --position-margin 0.01 --hand-position-margin 0.04 `
  --torsional-friction 0 --elliptic-friction 0 `
  --climb-com-weight 100 --climb-contact-stabilization velocity `
  --climb-com-inset 0.01 --climb-ankle-roll-margin 0.04 --climb-ankle-pitch-margin 0.04 `
  --relay 1 --relay-dy 0.27 --relay-waist 0.35 --relay-standoff 0.4
```

这是 fresh v15 单次完整通过所用的控制参数，尚未验证重复成功率。上述五个爬凳参数必须显式传入；共享控制器默认仍关闭 COM 软目标，使用原参考接触约束，COM inset 为 0，踝规划余量为 0.02 rad。本配置不启用 `--climb-position-guard`，物理关节范围和 0.001 rad 实际验收容差保持不变。

本机对应的解释器为 `D:/rsi_vla/genesis_env/Scripts/python.exe`；其他机器应替换为自己的环境路径。上述线程配置避免在线 IK 的线程争用，不构成物理可重复性的保证。

需要显式保留上述接力参数：程序默认的 `relay-dy`、`relay-waist`、`relay-standoff` 和 `self-collision` 与此命令不同。`--self-collision 0` 关闭机器人自碰撞，机器人与凳子、柜子、地面、箱子的碰撞仍参与物理计算。不要将该设置下的结果称为启用自碰撞后的成功。

fresh 验证不能带 `--resume-checkpoint`、`--start-at`、`--stop-after`，也不能改成 `--carry 0`。可额外加 `--save-checkpoint <新文件.pkl>` 保存诊断边界；只保存而不恢复，不改变 fresh 的身份。

## 独立验收

运行结束后执行：

```powershell
python -m humanoid.g1_support_retrieval.oracle.audit_chain $runDir --out "$runDir/audit.json"
```

当前审计含 55 项检查。只有全部通过，输出才会是 `classification=full_success`、`full_task_success=true`，进程退出码才为 0。失败、未完成或诊断运行返回非零；控制器自己的 `status=success` 不是完整验收结论。

主要证据要求如下：

- 从原始地面状态出发，阶段事件顺序完整，凳子实际离地搬运。使用凳子的实测起终点和搬运轨迹，不用机器人骨盆位移代替凳子位移。默认请求距离至少 1 m，净位移允许 0.08 m 位置容差；最终放凳点距计划落点不超过 0.04 m。因此报告应给实测距离，并称“约 1 m”。
- 放凳验收在退手、收臂之后：凳底距地不超过 0.015 m、倾斜不超过 10°、线速度不超过 0.03 m/s、角速度不超过 0.1 rad/s、双手与凳接触力之和小于 1 N，连续稳定至少 0.5 s。机器人同时必须站稳：根部高度至少 0.55 m、骨盆倾斜不超过 25°、双脚各有超过 20 N 支撑力、足底在地面附近、质心支持余量至少 0.005 m，并满足速度门控。只有凳子稳定而机器人倒地不能通过。
- 箱子实测释放在 0.90 m 板上；机器人空手下凳，再从地面姿态取箱。终点使用 `task_spec.py` 的目标区定义和实际箱子位置，不能只使用曾经出现过的任务成功标志。
- 最终箱子中心必须在目标区内且高度小于 0.35 m；按实际旋转后的八个角计算最低点，要求距地小于 0.015 m、线速度小于 0.03 m/s、角速度小于 0.1 rad/s、每只手的箱子接触力小于 1 N，连续至少 0.5 s。稳定侧躺可以交付；仍被手托着或落在目标区外不能通过。当前末端采用物理释放后落地稳定，不等同于双手一直托至地面的轻放。
- 所有阶段，包括嵌套 continuation、下凳和导航，都必须通过实际执行器检查，不能用上凳成功标志覆盖后续失败。

`scene.step` 后以 **200 Hz（每 5 ms）** 读取全部 **43 个关节**的实际控制力矩、速度和位置，累计整轮峰值；控制参考更新为 50 Hz。`physical` 使用模型的真实额定力矩上限，审计允许力矩和速度比不超过 1.001、关节硬限位越界不超过 **0.001 rad**。位置目标的 0.01/0.04 rad 安全余量并未放宽模型硬限位；目标没有越限也不能代替实际位置检查。阶段前缀检查是累计值，不应当作某个单独阶段的峰值。

## checkpoint 的用途与边界

`--save-checkpoint` 保存真实物理边界状态，包含抬凳完成（`lift`）、站起、搬运终点、下降末段、退手后、最终放凳和凳上状态。恢复时使用 Genesis 状态恢复接口，运行报告写入 `diagnostic_resume` / `checkpoint_resume` 和 `end_to_end_from_initial_state=false`。这种恢复包含状态写入，只用于定位下游问题；无论尾段是否成功，完整审计都保持 `partial_diagnostic`。

正常 fresh 流程没有把物体附着到手上，没有运行中改写机器人或物体位姿来完成动作；场景初始化位置写入除外。程序在初始化后关闭终止自动 reset，成功或跌倒时保留真实状态，继续观察释放和稳定情况。诊断的 `--start-at climb/relay` 也改变初始状态，不能当作完整远处搬凳实验。

凳上 checkpoint 保存在取箱控制器初始化之前。fresh 与凳上恢复都进入同一个 `prepare_retrieval` 路径；当前肩姿准备使用绝对目标并防止重复执行。不要在恢复分支额外调用一次肩姿过渡，再让取箱入口重复调用。

## 已修正的问题与历史失败

- 搬凳不能靠步数宣布完成：当前按实测凳子、落脚接触、双脚支持和终点稳定门控推进。放凳根据实际搬运末姿态下降，退手使用几何净空及手力反馈；收臂保持脚位和质心，并检查最终机器人站姿。历史 `setdown-tail-v14` 曾出现“凳子已放稳但机器人收臂后倒地”，现已增加独立机器人稳定门控。
- 爬凳入口曾因参考突跳导致左踝越限：当前先生成整段 IK 参考，再限制关节和根部速度、加速度，并保留实测触地与平衡门控。v28 已物理通过这一入口和上凳阶段。
- 旧上凳肩姿曾使手碰柜子前立柱：已按真实柜体几何检查整条参考路径，并将本链上凳肩 pitch 改为 −0.075 rad；共享规划器默认值保持不变。v28 上凳通过，但新的初始肩姿随后使取箱 IK 进入不合适的分支，推移箱子。新增凳上双支撑肩姿过渡回 −0.15 rad 后，v29 已物理完成尾段；过渡只执行一次，实际双肩误差约 0.00105 rad、质心误差约 0.20 mm，稳定 0.5 s 后开始取箱。
- 初始抬凳与站起曾使腰 pitch 在 50 N·m 上限持续饱和。当前腰 pitch 规划上限为 0.47 rad，相关阶段提高阻尼；真实抬凳完成后，先保持骨盆高度，将凳收近 0.06 m、抬高 0.08 m，再站起，减小前伸载荷。仅增加规划余量和阻尼并未解决先前的站起过载，减载路径是独立修正。
- v30 站起的旧 IK 先求出较大关节分支，再统一裁切参考增量，造成手部目标滞后与随后追赶；日志中抓持卸载先于记录到的肩肘擦凳，随后俯仰补偿饱和，稳定持凳失败。当前将关节步长约束纳入站起第二段 IK 求解，保留物理限位与实际审计。v31 已物理完成站起，力矩比 / 速度比 / 位置越限峰值为 `1.0 / 0.03714 / 0`；fresh v12 的抓凳与站起也通过，但后续行走失败。
- v12 暴露了站起到步行的姿态衔接问题：站起未约束骨盆侧倾，步行却固定继承该姿态；每步又沿用偏移后的实测脚道。当前站起末段逐渐归正骨盆，只在摆动脚腾空后恢复初始横向脚道；步行 IK 增加 1° 足姿态验收，步行 WBC 增加多时刻预测位置约束并在不满足时停止。v32 恢复诊断和 fresh v13 均已物理完成 18 步搬运，实际关节越限为 0，关节物理限位和最终审计容差保持不变。
- v13 已物理通过新的搬运和放凳，但实际落凳朝向约为 −5.45°，改变了爬凳时的手柜净空。共享爬凳规划器只包含地面和凳子，旧肩姿在该朝向下碰到柜前立柱。当前仅本链将肩 roll 幅度从 0.5 收至 0.4 rad；双脚上凳后平衡过渡回取箱的 pitch −0.15、roll ±0.5。正式上凳和肩姿过渡执行前，用真实柜体碰撞盒检查世界坐标参考，要求至少 25 mm 净空。当时 CPU 候选全路径净空约 41.65 mm，肩姿过渡约 64.51 mm；后续还需结合重心及踝余量修正，才在 fresh v15 完成整链。
- v33 排除了失稳前再次碰柜，但暴露了上凳控制的重心偏差：参考足朝向约 0°，负重实际左足朝向约 −11.4°；控制器仍要求按参考足位置加速纠偏，而实际重心已经向外偏约 16 mm。离线重建的旧 QP 此时还预测向外加速度。新增可选 XY 重心加速度软目标及按实际接触速度稳定的约束，默认不影响共享控制器。v34 的 `--climb-com-weight 100 --climb-contact-stabilization velocity` 已物理通过尾段：抬右脚后的前移阶段实际 COM 跟踪误差最大 2.34 mm，实测左脚支撑余量最少 7.51 mm，但左踝仍有持续软限位接触。v35 的额外 `--climb-com-inset 0.01` 改善了支撑余量，仍未消除踝越界，最大实际越限为 0.00141758 rad。下凳重规划也继承 COM inset 参数，不能直接沿用 v34 的下凳结论。正式爬凳新增 20 ms 实测状态、参考、求解力矩、接触力及凳子姿态日志；肩准备、取箱及下凳不启用新的 COM/接触/预测限位控制选项。
- v36 在正式上凳期间启用已有多时刻关节位置预测约束 `--climb-position-guard 0.02`；该数值是控制器预留，不是放宽物理关节范围或 0.001 rad 验收容差。1824 个已执行控制步的 QP 均求解成功，预测约束最大残差约 7.01×10⁻⁷ rad；但最后一步（639.28–639.30 s）左踝 roll 实际位置从 0.235612 变为 0.256453 rad，20 ms 预测位置却为 0.226506 rad，差 29.948 mrad。实际速度从 −0.584622 变为 +1.211257 rad/s，下一次求解因加速度界不相容而拒绝。停止前的实际力矩比 / 速度比 / 位置越限峰值为 `0.480718 / 0.0358895 / 0`，未到达双脚凳上验收。末尾 `actuators:stage_end` 仅记录阶段函数退出时的累计执行器检查，不表示该动作完成；失败求解本身没有控制轨迹行，可用最后成功步的实测末状态与保存的参考重建。预测模型与接触中的实际响应偏差仍待修正。
- v37 保留重心与接触修正，不启用预测位置约束，仅将踝 roll 的 IK 规划余量增至 0.04 rad。全部 3408 个正式控制步 QP 均可解，也到达双脚凳上，但左踝 pitch 实际达到 −0.873859107 rad，低于物理下界 −0.87267 rad；实际跟踪没有保住规划余量。左踝 roll 仍有 0.00076478 rad 名义越界，虽未超过验收容差，也不能宣称有 0.04 rad 实测余量。整轮峰值为 `1.0 / 0.0773957 / 0.001189113`，主动停止前已失败。凳上 checkpoint 的数组到标量转换错误已另行修正；这项保存修复不改变上述物理结果。
- v38 将踝 pitch/roll 规划余量同时设为 0.04 rad，恢复后的完整尾段通过，凳上 checkpoint 也成功保存。实测左踝 pitch 仍有约 4.138 mrad（即 0.004138 rad）下界余量；roll 最大名义越界 0.0006468594 rad，在原 0.001 rad 容差内，不能称为零越界或 0.04 rad 实测余量。凳上 checkpoint 仅保存 continuation 的 50 Hz 峰值；本轮实际 200 Hz 通过结论来自后续阶段及终局的完整监控报告。
- 凳上腰参考已限制速度（0.35 rad/s）和加速度（0.8 rad/s²），并以真正下发的参考计算手部误差；箱子和环境接触每步刷新。末端交付加入实际落点与持续稳定检查；上凳报告把 `climb_success` 与整个 continuation 的 `success` 分开，避免后续失败被覆盖。

## 记录与复核

每轮目录保存 `config.json`、`events.jsonl`、`motion.mp4` 和终局 `result.json`；运行到 continuation 时还有对应报告和关节轨迹。报告包含搬运轨迹、释放轨迹、执行器峰值、43 关节位置极值及失败原因。异常退出、失败和主动停止的记录均应保留；使用新输出目录，不覆盖历史失败来只保留成功录像。硬杀进程可能来不及写终局报告，缺失 `result.json` 不能解释为成功。

当前入口归档 24 个选定源码/配置文件到 `sources/`，包括入口、checkpoint、步行与入口参考模块、真实柜体净空检查、审计器，以及相关共享控制器和任务配置；加入柜体检查前的相应历史运行归档 23 个文件。它们不是整个 Python/CUDA 环境的完整快照；复现还应核对依赖与资源版本。v28 在启动后补存了 8 个启动时未归档、内容未变的共享文件，补存原因和 SHA 见 [`source_snapshot_supplement.json`](runs/entry-clearance-tail-v28/source_snapshot_supplement.json)，原始入口快照未覆盖。后续运行已把这 8 个文件纳入启动归档。

查看录像时应同时核对事件时间和实测轨迹；单帧到位、采样接触日志中没有接触、或一张最终截图都不能替代完整物理与来源审计。checkpoint 续跑的 `sim_seconds` 延续原始时钟，计算本轮速度应减去恢复时刻，不能把最终时钟全部算成本轮模拟时长。
